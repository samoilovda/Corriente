## 0. Как работать в этом репозитории (обязательно прочитать)

**Что за проект.** Corriente — офлайн-учёт личных финансов: Android-приложение (`:app`, `:widget`), общий слой данных
(`:core:data`, `:core:money`), его JVM-сборка для компьютера (`:core:data-jvm`) и окно для компьютера (`:desktop`,
Compose Desktop). Синхронизация между устройствами — через общую папку Syncthing, без сети в приложении.

**Прочитать перед началом:**
* `docs/INVARIANTS.md` — инварианты; их нарушение = дефект, даже если тесты зелёные. Особенно: I-1 (деньги — только
  `Long` минорных единиц, никаких `Float`/`Double`), I-3 (арифметика сумм — только через `Money`), I-8 (разные валюты не
  складываются), I-20 (никакого `fallbackToDestructiveMigration`, каждая миграция — объект с тестом), I-22/I-26/I-27
  (синхронизация), I-24 (**в приложении нет сетевого кода и разрешения INTERNET** — ни на Android, ни на десктопе),
  I-25 (форматирование/разбор денег не зависит от локали).
* `docs/SYNC_DESIGN.md` — устройство синхронизации (особенно §2–§4, «Уточнения, найденные тестом сходимости», §7, §9).
* `docs/ARCHITECTURE.md` — ADR, ручной DI (`AppContainer`), почему нет Hilt/сети.
* `README.md` — сборка, версии, синхронизация, десктоп.

**Правила работы:**
1. Новая ветка от `024e5bb`, например `agent/followups-2026-10`. **Не пушить и не мерджить** — владелец посмотрит сам.
2. Одна задача = один или несколько коммитов с префиксом её номера (`T2: …`). Сообщения коммитов — на русском, как в
   истории (`git log`). Комментарии в коде — на русском, в стиле окружающего кода (с отсылкой к задаче/инварианту).
3. **Схему БД не менять.** Текущая версия — 8 (`AppDatabase.SCHEMA_VERSION`). Владелец может в любой момент поставить
   эту сборку на телефон, поэтому правка «внутри» схемы 8 сломает ему установку. Ни одна задача ниже схему менять не
   должна; если окажется, что без этого никак, — остановиться и описать это в отчёте, а не менять.
4. Не ставить сборки на реальные устройства. К компьютеру по adb могут быть подключены телефон и планшет владельца
   (по Wi-Fi). Все adb/Gradle-команды для устройства — **только с `ANDROID_SERIAL=emulator-5554`** (эмулятор AVD
   `corriente`, запуск: `$ANDROID_HOME/emulator/emulator -avd corriente -no-audio -no-snapshot-save`).
   Инструментальные тесты стирают данные приложения на эмуляторе — это нормально.
5. Новые зависимости — только если без них никак, с объяснением в коммите (`BUILD_PLAN.md` §1.3 — закрытый список).
   Сетевых библиотек — никогда.
6. Тексты интерфейса Android — в `res/values/strings.xml` (ru) и `res/values-en/strings.xml` (en), обе локали.
   Десктоп пока только на русском (строки в коде) — так и оставить.
7. Обновлять документацию вместе с кодом: `CHANGELOG.md` (секция `[Unreleased]`), `docs/SYNC_DESIGN.md` (статус этапов),
   `README.md` — если меняется то, что там описано.

**Проверка перед каждым коммитом:**
```
./gradlew check                                  # юнит-тесты, lint, verifyInvariantGuards (сканер инвариантов)
./gradlew :core:data-jvm:test                    # слой данных на JVM (десктоп), включая синхронизацию
ANDROID_SERIAL=emulator-5554 ./gradlew connectedCheck   # инструментальные тесты на эмуляторе
./gradlew :desktop:compileKotlin                 # десктоп собирается
```
`verifyInvariantGuards` запрещает `Float`/`Double` и `.toFloat()/.toDouble()` вне файлов из `floatAllowlist`
(`buildSrc/.../InvariantGuards.kt`) — туда добавляются только файлы, где дробные числа нужны для координат отрисовки.

Эталон «зелёного» состояния на `024e5bb`: `check` ок; `connectedCheck` — `core:data` 55/55, `app` 21/21 (один тест
нестабилен — это задача T5); `:core:data-jvm:test` 2/2.

## T1. Нестабильный тест `ShortcutRecreateInstrumentedTest`

**Проблема.** `app/src/androidTest/.../navigation/ShortcutRecreateInstrumentedTest.kt` иногда падает в полном
`connectedCheck` с `IllegalStateException: Requested a re-creation of Activity but didn't happen`
(`ActivityScenario.recreate`). Отдельно проходит стабильно — значит, это гонка на медленном эмуляторе (Activity ещё
не в `RESUMED` или идёт другая анимация/переход), а не дефект приложения.

**Что сделать.** Сделать тест устойчивым: дождаться устойчивого состояния перед `recreate()` (например,
`scenario.moveToState(Lifecycle.State.RESUMED)` + `waitForIdle`/ожидание нужного узла через `composeRule.waitUntil`),
не меняя того, что тест проверяет (после пересоздания ярлык не «проигрывается» повторно). Код приложения не трогать,
если только не найдена реальная причина в нём — тогда описать её.

**Готово, когда:** полный `connectedCheck` три раза подряд зелёный (приложить в отчёт числа тестов каждого прогона).

## T2. Подпись нижней навигации переносится по слогам на узком экране

**Проблема.** На экране ~360×640 dp с крупным шрифтом (`font_scale 1.3`) подпись «Transactions» во вкладке нижней
навигации ломается по слогам («Transactio / ns»). Место — `app/.../navigation/CorrienteNavHost.kt`
(`NavigationBarItem`, `label`), подписи — `CorrienteDestination` (`labelRes`).

**Что сделать.** Подпись в одну строку без переноса по слогам (`maxLines = 1`, `softWrap = false`, обрезка с
многоточием или уменьшение текста для длинных подписей). Переименовывать пункты не нужно.

**Как проверить (сценарий из `docs/AUDIT_2026-09-23.md` §8.4):**
```
adb -s emulator-5554 shell wm size 720x1280
adb -s emulator-5554 shell wm density 320
adb -s emulator-5554 shell settings put system font_scale 1.3
# английская локаль приложения: Настройки → Язык → English
```

**Готово, когда:** на этом экране все четыре подписи читаются в одну строку на русском и английском (скриншоты в

## T3. Синхронизация: одинаковые бюджеты с двух устройств

**Проблема.** `docs/SYNC_DESIGN.md` §4 обещает: «Бюджет одной категории создан на обоих устройствах → дубликат по
`(категория, валюта, период)` сливается, побеждает меньший id». Это **не реализовано**: сейчас после синхронизации
будет два бюджета на одну категорию и валюту.

**Где.** `core/data/src/main/kotlin/com/corriente/data/sync/SyncEngine.kt` (`applyUpsert`; образец — как устроено
`resolveCategoryNameClash`). Бюджет: `BudgetEntity` (`id`, `category_id` — может быть `NULL` = «на всё»,
`currency_code`, `period`, `starts_on`). На бюджеты никто не ссылается — перенаправления не нужны.

**Как.** При применении чужой строки `budget`: если есть другой бюджет с тем же ключом дубля
`(category_id, currency_code, period)` (с учётом `NULL` у `category_id`) — победитель — меньший `id`, проигравший
удаляется. Важно (см. «Уточнения, найденные тестом сходимости» в `SYNC_DESIGN.md`): производные правки делаются **как
локальные изменения** (через `asLocalChange`, чтобы удаление проигравшего ушло на другие устройства), иначе итог
зависит от порядка получения файлов и устройства расходятся. Если проигрывает пришедшая строка — не вставлять её и
поставить её `sync_row_meta` в надгробие (как с категориями). Учесть ключ после перенаправлений категорий
(`category_redirect`): бюджет мог прийти на слитую категорию. Проверить, как локальное создание бюджетов защищено от
дублей на одном устройстве (`BudgetRepository`), и не сломать это.

**Тесты.**
* В `core/data/src/androidTest/.../sync/SyncConvergenceInstrumentedTest.kt` — сценарий: телефон и планшет независимо
  создают бюджет на одну категорию и валюту → после обмена до тишины ровно один бюджет с меньшим id на обоих.
* В случайный тест сходимости (`randomOperationsOnThreeDevicesConverge`) добавить операции с бюджетами (создание,
  изменение суммы, удаление) и сравнение таблицы `budget` (она уже входит в `dump`).
* Разово (не коммитить изменённые числа) прогнать случайный тест с 40 сидами × 250 шагов — должен сойтись.
* По возможности — тот же сценарий в JVM-тест `core/data-jvm/src/test/.../DesktopSyncTest.kt`.

**Готово, когда:** тесты выше зелёные, строка про бюджеты в `SYNC_DESIGN.md` §4 соответствует реализации.

## T4. Синхронизация: очистка папки (этап S5)

**Проблема.** Каждое устройство пишет файл `changes/<deviceId>/<seq>.json` на каждый обмен с изменениями
(на телефоне — до нескольких в минуту при активном вводе). Файлы не удаляются никогда; через год это тысячи файлов,
и каждый обмен через SAF на Android будет перечислять их все. План — `docs/SYNC_DESIGN.md` §7.

**Что сделать** (код — в `SyncEngine`/`SyncFiles.kt`, `:core:data`; UI — Android и десктоп):
1. **Снимок.** Устройство пишет `snapshots/<deviceId>.json` — полное текущее состояние синхронизируемых строк с их
   версиями (`sync_row_meta.hlc`) и надгробиями, плюс `seq`, по который он актуален. Формат — новый тип файла рядом с
   `ChangeFile`; поднять `ChangeFile.FORMAT_VERSION` до 2 и документировать в `SYNC_DESIGN.md` §3. Снимок применяется
   тем же LWW, что и обычные изменения (он ничем не «главнее»).
2. **Удаление своих файлов.** Устройство удаляет **только свои** `changes/<self>/<seq>.json` с `seq` ≤ минимального
   `seen[self]` среди карточек других устройств (`devices/*.json`, поле `seen`). Устройство, которое не обновляло
   карточку больше 90 дней, очистку не блокирует.
3. **Подключение после очистки.** Новое или давно отсутствовавшее устройство, у которого курсор устройства меньше
   первого сохранившегося файла, сначала применяет снимок этого устройства, затем файлы после его `seq`.
4. **Надгробия** в `sync_row_meta` старше 90 дней (по времени HLC) удаляются.
5. **Когда.** Автоматически не чаще раза в сутки, когда своих файлов больше порога (например, 200), плюс кнопка
   «Очистить журнал синхронизации» на экранах синхронизации (Android `ui/sync/SyncScreen.kt`, десктоп
   `desktop/.../SyncScreen.kt`) с коротким пояснением, что данные не удаляются.
6. Старые версии приложения: устройство, которое ещё на формате 1, не должно потерять данные — раз оно не может
   прочесть снимок, очистка не должна удалять файлы, которые оно не применило (это уже обеспечивает п. 2, если
   устройство пишет `seen`). Описать это в `SYNC_DESIGN.md`.

**Тесты** (инструментальные `core:data` и/или JVM `core:data-jvm`):
* после очистки на устройстве A его старые файлы удалены, только если B и C их применили;
* новое устройство D подключается после очистки (снимок + хвост) и сходится с остальными;
* устройство, «пропавшее» на 91 день (через подмену `now` в `SyncEngine`), не блокирует очистку, а вернувшись —
  подключается заново через снимок и сходится;
* случайный тест сходимости с периодической очисткой в случайные моменты — сходится.

**Готово, когда:** тесты зелёные; `SYNC_DESIGN.md` §3, §7, §9 (S5 ✅) обновлены; на эмуляторе проверено, что кнопка
работает и после неё обмен продолжается (папка: `/sdcard/Corriente-sync`, выбрать через пикер на экране
синхронизации; второй «устройство» можно имитировать файлами, положенными через `adb push`, — см. как это сделано в
истории коммитов S3).

## T5. Десктоп: автотесты интерфейса и мелкие дефекты

**Проблема.** Окно для компьютера (`:desktop`) проверено только визуально (главный экран отрисовывается на тестовых
данных). Ввод, правка, удаление в окне и экран синхронизации не проверены ни руками, ни тестами.

**Что сделать.**
1. Подключить тестовую зависимость Compose Desktop для UI-тестов (`compose.desktop.uiTestJUnit4` /
   `org.jetbrains.compose.ui:ui-test-junit4` той же версии, что плагин) и написать тесты на `DesktopContainer` с
   временной папкой данных (переменная `CORRIENTE_DATA_DIR` или конструктор с `dataDir`):
   * пустая база без счетов — подсказка «Счетов пока нет…»;
   * с одним счётом: «− Расход» → ввод суммы → категория → «Сохранить» → операция в списке, кольцо и баланс
     обновились; Enter в поле суммы тоже сохраняет;
   * правка суммы и удаление операции из окна правки;
   * клик по иконке категории на кольце открывает расход с уже выбранной категорией;
   * неверный ввод (0, пусто, дата не `ГГГГ-ММ-ДД`) — сообщение об ошибке, ничего не записано.
2. Дефекты, известные заранее:
   * `EntryDialog.kt`: при смене счёта на счёт в другой валюте сумма не пересчитывается под точность новой валюты
     (строка `amountText = amountText` — пустышка). Пересобирать ввод через `AmountInput.fromText(…, новаяВалюта)` или
     сбрасывать сумму — как на Android (`TxnEntryViewModel.selectAccount`).
   * При запуске из исходников (`./gradlew :desktop:run`) в меню macOS программа называется «MainKt». Для запуска из
     Gradle — задать имя (`-Xdock:name=Corriente` в `jvmArgs` только на macOS или `System.setProperty("apple.awt.application.name", …)`
     до создания окна). В собранном `.dmg` имя уже правильное — не сломать.
   * Убедиться, что фоновой обмен (`DesktopSync.start`) не мешает закрытию окна (процесс завершается сразу).
3. `./gradlew :desktop:packageDmg` после изменений собирается (на macOS).

**Готово, когда:** UI-тесты десктопа зелёные и входят в `./gradlew check` (или отдельной командой, описанной в README),
дефекты исправлены, `.dmg` собирается.

## T6. Версия 0.4.0 (делать последней)

**Почему.** С 0.3.0 изменились схема БД (7 → 8), появились синхронизация, иконки категорий, новый главный экран,
десктоп. По правилу из `README.md` («Версии») — новый `versionCode` для любой сборки, которая уйдёт на устройство, и
`MINOR` за этап с заметными для пользователя изменениями.

**Что сделать.**
* `gradle/libs.versions.toml`: `appVersionCode = "4"`, `appVersionName = "0.4.0"`.
* `CHANGELOG.md`: содержимое `[Unreleased]` перенести в новую секцию `## [0.4.0] — versionCode 4` (оставить пустую
  `[Unreleased]`), сгруппировав так же, как устроены предыдущие релизы.
* `README.md` («Версии»): одна строка о 0.4.0 (схема v8, синхронизация, десктоп).
* Версия десктопа (`desktop/build.gradle.kts`, `packageVersion`) живёт отдельно: на macOS `MAJOR` у пакета должен быть
  ≥ 1, поэтому там `1.x.y`. Оставить `1.0.0`, но вынести в `libs.versions.toml` рядом с версией приложения
  (`desktopVersion`) и одной фразой описать в README.

**Готово, когда:** `check` зелёный, собранный debug-APK показывает 0.4.0 (`aapt2 dump badging` или «О приложении»).

## Чего НЕ делать (требует владельца)

* Устанавливать что-либо на телефон/планшет владельца (`scripts/deploy.sh` без `ANDROID_SERIAL=emulator-5554`).
* Живая проверка синхронизации через Syncthing на реальных устройствах (этап S4) — делает владелец.
* Установщики для ThinkPad (`.msi`/`.deb`): ОС не выбрана, собираются только на целевой системе.
* Подпись релизной сборки (`assembleRelease` без ключей не соберётся — так задумано; ключи не создавать).
* Любые изменения схемы БД, сетевой код, отказ от инвариантов, CI/публикация в GitHub.
* Пункт BACKLOG про английский эталон `testdata` — условный («при появлении английского эталона»), сейчас делать нечего.
