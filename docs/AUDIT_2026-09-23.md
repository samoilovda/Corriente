## 2. Общая картина

Архитектура и дисциплина проекта сильные: деньги только в `Long` минорных единиц, арифметика через
`Math.*Exact`, курс нигде не хранится, сети нет, инварианты проверяются статическим стражем,
400 юнит-тестов и инструментальные тесты БД/UI. Предыдущие раунды (`FIX_PLAN`, R1–R6, три
пост-релизных фикса) закрыли очевидные классы ошибок.

Оставшиеся дефекты группируются в пять системных слабых мест — на них стоит смотреть и при
ревью будущих задач:

1. **Исключения вне `launchWrite`.** F0.2 завёл безопасный путь записи, но вычисления в
   `form.update {}`, в `combine` и в `viewModelScope.launch` без обработчика по-прежнему роняют
   процесс: калькулятор (A0.2), список файлов автобэкапа (A1.3), SAF-потоки в колбэках экранов
   (A2.1), FX-отчёт (A2.14), пересчёт по курсу (A2.6).
2. **«Сегодня», захваченное один раз.** Долгоживущие потоки фиксируют дату при подписке:
   виджет (A1.2); список операций ограничен «завтра» (A2.7).
3. **Таблицы R2 (`budget`, `recurrence`) не учтены в старых путях.** Удаление, слияние, откат
   импорта, смена валюты счёта знают только про `txn` (A1.6, A1.7, A1.5), правка правила не знает
   про уже созданные операции (A0.1).
4. **Решения экрана импорта, не доведённые до записи** (A1.8), и неполный откат (A1.9).
5. **Надёжность бэкапа** держится на `validate`, который проверяет не всё, что потом бросает
   `toEntity()/toDomain()` (A1.12), плюс неатомарная запись/экспорт (A1.13, A1.14).

## 3. P0 — падает или молча пишет неверные данные

### A0.1 — Правка повторяющегося правила создаёт лишнюю операцию `[БД]`

**Симптом.** Правило «каждые 30 дней, аренда 50 000 ₽» создало операцию 20-го. 23-го пользователь
исправляет заметку правила → при ближайшем запуске воркера появляется ещё одна «аренда» датой
23-го, а расписание съезжает на 23-е. Для «каждый месяц N-го» то же происходит, если правка
сделана в день N после того, как операция уже создана. Дубликат выглядит как обычная операция —
пользователь его может не заметить, баланс тихо неверен.

**Причина.** `RecurrenceRepository.update` всегда пересчитывает расписание от сегодняшней даты:
`nextRunOn = firstOccurrenceOnOrAfter(rule, today)` (`DATA/repository/RecurrenceRepository.kt:74`).
Для `EveryNDays` эта функция возвращает саму `from` (`DATA/recurrence/RecurrenceRule.kt:40`), для
`DayOfMonth` — сегодняшнюю дату, если сегодня день N (`:41-45`). Уже материализованная дата снова
попадает в `dueDates`. Вызов — `RecurringViewModel.save` (`APP/ui/recurring/RecurringViewModel.kt:172-198`).
Юнит-тестов на `update` нет.

**Что сделать.**
1. Если правило (тип + параметр) не изменилось — `nextRunOn` не трогать: правка суммы, заметки,
   счёта, категории действует со следующего запуска.
2. Если правило изменилось — `nextRunOn = firstOccurrenceOnOrAfter(newRule, lowerBound)`, где
   `lowerBound = maxOf(today, lastMaterializedDate + 1 день)`. `lastMaterializedDate` — дата
   операции `lastCreatedTxnId` (если есть и не удалена); если её нет, но `existing.nextRunOn > today`
   (сегодняшняя дата уже обработана) — `lowerBound = today + 1`.
3. Инвариант, который фиксирует KDoc `update`: *после правки ни одна дата ≤ даты последней
   созданной правилом операции не может снова оказаться в `dueDates`*.

**Критерий приёмки.** Правка любого поля правила — в день срабатывания и в любой другой — не
создаёт дополнительной операции; изменение интервала/дня сдвигает расписание только вперёд.

**Тесты.**
* Юнит (`RecurrenceRepository` на фейковом DAO): (а) `EveryNDays(30)`, материализовано 3 дня назад,
  правка заметки → `nextRunOn` не изменился; (б) `DayOfMonth(23)`, сегодня 23-е и операция уже
  создана, правка суммы → `nextRunOn` = 23-е следующего месяца; (в) `EveryNDays(30) → EveryNDays(7)`
  → `nextRunOn` строго позже даты последней операции.
* `[БД]` `RecurrenceMaterializerInstrumentedTest`: materialize → update → materialize в тот же день
  → ровно одна операция.

### A0.2 — Калькулятор суммы роняет приложение при переполнении

**Симптом.** На экране ввода набрать `1000000000 × 1000000000` (или `÷` при крупной сумме, или
несколько раз `+` максимальной суммы) → приложение закрывается. Тот же класс дефекта, что F0.1
(P0), вернувшийся вместе с `× ÷`.

**Причина.** `applyCalc` по I-3 бросает `ArithmeticException` (`MONEY/Calculator.kt:23-30`) — это
правильно и покрыто `CalculatorTest`. Но вызывающий код исключение не ловит:
* `TxnEntryViewModel.pressOp` / `pressEquals` (`APP/ui/txnentry/TxnEntryViewModel.kt:396-423`) —
  внутри `form.update {}` на главном потоке;
* `TxnEntryUiState.resolvedMinor()` (`:106-115`), который зовут `canSave` и `nonPositiveResult`, —
  внутри `combine` (`:289-352`) и прямо в композиции `TxnEntryScreen`.

Дополнительно `×` переполняется уже на промежуточном `acc × operand` — до деления на
`10^minorUnits`, то есть раньше, чем результат перестаёт помещаться в `Long`. А результат, который
в `Long` помещается, но длиннее лимита `AmountInput` (18 цифр), `AmountInput.fromMinor` соберёт в
строку длиннее лимита — снова путь F0.1.

**Что сделать.**
1. В `TxnEntryViewModel` — одна безопасная функция вычисления (`applyCalc` в `try`); при
   переполнении форма не меняется, выставляется сообщение (новый ресурс «Слишком большое число»
   в обеих локалях); `resolvedMinor()` возвращает `null` → `canSave == false`.
2. Результат длиннее лимита `AmountInput` считать переполнением.
3. (Опционально) убрать ложное переполнение `×`: промежуточное произведение — через
   `Math.multiplyHigh`/`BigInteger` как транзитный тип, проверка — после деления.

**Критерий приёмки.** Никакая последовательность нажатий клавиатуры не роняет экран; при
переполнении видно сообщение, «Сохранить» недоступна, `⌫` возвращает к валидному вводу.

**Тесты.** `TxnEntryViewModelTest`: «15 девяток `×` 999999 `=`», «максимальная сумма `÷` 0.01»,
«10 раз `+` максимальная сумма» — без исключения, `canSave == false`, сообщение выставлено;
`CalculatorTest` — при необходимости на п.3.

### A1.1 — «Показать ещё» в списке операций почти никогда не появляется `[БД]`

**Симптом.** После импорта многолетней истории Monefy список показывает только последние 3 месяца;
кнопки «Показать ещё» нет. Старые операции видны только через поиск или фильтр по датам. CSV
списка тоже выгружает только эти 3 месяца.

**Причина.** `APP/ui/transactions/TransactionsViewModel.kt:340-342`:

### A1.2 — Виджет после полуночи пересчитывается по «вчерашней» дате `[ручная]`

**Симптом.** Процесс приложения прожил через смену суток/месяца (обычное дело при размещённом
виджете). В полночь `WidgetMidnightWorker` рисует верный снимок, но первая же новая операция
возвращает на виджет траты прошлого месяца, а операции, датированные новым днём, в «расходы за
месяц» и «частые категории» не попадают вовсе.

**Причина.** `WidgetUpdater.start()` (`APP/widget/WidgetUpdater.kt:77-93`) вычисляет `now = today()`
и `windowStart` один раз внутри `flatMapLatest`, который перезапускается только при смене факта
размещения виджета (`distinctUntilChanged` по `Boolean`). Подписка `observeRange(windowStart, now)`
(верхняя граница — «сегодня» момента подписки) и `assemble(d, config, now)` живут с этой датой,
пока жив процесс. `refreshNow()` (`:111-123`) делает разовый снимок и долгую подписку не
перезапускает — следующая запись в БД затирает верный снимок устаревшим.

**Что сделать.** Сделать дату частью реактивного ключа: `dateTicker: Flow<LocalDate>` (эмитит
`today()` сразу и на каждой полуночи; дополнительно — по сигналу из `refreshNow`/
`WidgetMidnightWorker` и при смене времени/часового пояса) и `flatMapLatest` по паре
`(placed, date)`. Альтернатива без тикера: окно с открытой верхней границей и `today()`,
вычисляемый в `assemble` на каждой эмиссии.

**Критерий приёмки.** После смены даты при живом процессе снимок, пересчитанный по записи в БД,
использует новую дату: месяц трат, окно частых категорий, операции «сегодня».

**Тесты.** Вынести построение потока в функцию с инжектируемыми `today`/тикером; юнит: эмиссия
новой даты + новая операция → `monthExpenses` нового месяца. `[ручная]` — §8.2.

### A1.5 — Повторяющиеся: одно сломанное правило останавливает все; материализация не атомарна `[БД]`

**Симптом.** Если одно правило не записывается (например, после A1.6 — валюта счёта изменилась),
воркер падает на нём, делает 3 ретрая и `failure` — и так каждый день; правила, стоящие в списке
после него, не исполняются никогда. Если процесс умирает между вставкой операций правила и
`recordRun`, следующий запуск создаёт те же даты повторно.

**Причина.** `RecurrenceMaterializer.materializeDue` (`APP/recurring/RecurrenceMaterializer.kt:33-48`)
— общий `forEach` без изоляции ошибок; вставки (`TxnRepository.addExpense/addIncome`) и
`recurrences.recordRun` (`:47`) — отдельные транзакции. `RecurrenceWorker.doWork`
(`APP/recurring/RecurrenceWorker.kt:31-33`) ловит исключение целиком.

**Что сделать.**
1. Для каждого правила — одна транзакция БД «все операции правила + `recordRun`» (метод в
   `:core:data`, например `RecurrenceRepository.materialize(rule, dates, marker)` через
   `db.withTransaction`; проверка `requireValidTxn` — та же, что сейчас).
2. Ошибка одного правила не прерывает остальные: копить ошибки, показывать на экране
   «Повторяющиеся» (ключ `recurrence.last_error.<id>` в `app_setting` — без миграции).
3. Воркер: `success`, если цикл прошёл; `retry` — только при общей ошибке (БД недоступна).

**Критерий приёмки.** Правило с ошибкой не мешает остальным; прерывание посреди правила не оставляет
половины операций и не порождает дублей.

**Тесты.** `[БД]` `RecurrenceMaterializerInstrumentedTest`: правило с несовпадающей валютой +
валидное → валидное материализовано, ошибочное помечено; исключение после первой вставки
(фейковый писатель) → ни одной операции этого правила, `nextRunOn` не сдвинут.

### A1.7 — FK бюджетов и правил ломают удаление, слияние и откат импорта `[БД]`

**Симптом.**
* Удалить категорию/счёт, на которые ссылается бюджет или правило, нельзя — «Не удалось удалить»
  без объяснения.
* Слияние категорий, у исходной есть бюджет/правило, — «Не удалось объединить».
* **Откат импорта невозможен**, если пользователь успел завести бюджет или правило на
  импортированную категорию либо сделать её родителем своей подкатегории. По шкале приоритетов —
  «невозможность откатить ошибку».

**Причина.** R2.3/R2.4 добавили `budget.category_id`, `recurrence.account_id`,
`recurrence.category_id` — настоящие `@ForeignKey` с `NO ACTION` (Room выполняет
`PRAGMA foreign_keys = ON` — проверено в сгенерированном `AppDatabase_Impl`). Старые пути их не
знают:
* `AccountRepository.deleteIfUnused` (`DATA/repository/AccountRepository.kt:109-114`);
* `CategoryRepository.deleteIfUnused` (`DATA/repository/CategoryRepository.kt:80-85`) и
  `mergeInto` → `CategoryDao.merge` (`DATA/db/dao/CategoryDao.kt:51-55`) — переназначает только `txn`;
* `ImportBatchDao.deleteOrphanedImportCategoriesForBatch` (`DATA/db/dao/ImportBatchDao.kt:28-36`) —
  «осиротевшая» = без операций, но не без бюджетов/правил/подкатегорий.

**Что сделать.**
1. «Используется» = операции ∪ бюджеты ∪ правила (∪ подкатегории — для категорий), одним
   DAO-запросом. `deleteIfUnused` возвращает причину отказа (sealed), а не `false`.
2. `merge` в одной транзакции переносит на `intoId` также `budget.category_id` и
   `recurrence.category_id`. `[решение]`: если у `intoId` уже есть бюджет в той же валюте — оставить
   один (какой?) или запретить слияние; зафиксировать в KDoc.
3. SQL отката не удаляет категории, на которые ссылаются `budget`, `recurrence`, `category.parent_id`.
4. Тексты отказов на экранах — с причиной (связано с A2.2).

**Критерий приёмки.** Ни один из путей не падает на FK; откат импорта проходит всегда (оставляя
«занятые» категории и сообщая об этом).

**Тесты.** `[БД]` инструментальные: удаление категории с бюджетом → отказ с причиной; merge с
бюджетом/правилом → ссылки переехали, исходная удалена; импорт → бюджет на импортированную
категорию → rollback проходит, категория осталась, операции батча удалены.

### A1.8 — Импорт: конфликт валют одного счёта невозможно импортировать `[БД]`

**Критерий приёмки.** Файл с конфликтом импортируется после выбора решения, каждая операция — в
счёте своей валюты; без решения кнопка неактивна.

### A2.14 — FX-отчёт может упасть; оценка стоимости конвертаций грубая

**Причина.** `DATA/usecase/ConversionCost.kt:43` — деление на `deal.rateMicros`, `:91` — на `median`.

мусорная. `Math.multiplyExact(deviation, quoteMinor)` (`:91`) переполняется на крупных суммах — тоже краш.

**Что сделать.** Считать курс и отклонения в `BigDecimal` (это отношение сумм, не деньги; итог
округляется один раз до минорных единиц — I-4); защититься от нуля; VM — не падать (`try` вокруг
расчёта, «недостаточно данных» при ошибке).

**Тесты.** `ConversionCostTest` с курсом 1e-7, 1e-5 и крупными суммами.

копию, сделанную перед обновлением/восстановлением» через тот же путь `restore` с проверкой (или экспорт
копии в SAF) — `[решение]`.

**Тесты.** `[БД]`: копия после checkpoint открывается и содержит последнюю запись.

### A2.16 — Восстановление переносит настройки, привязанные к устройству `[БД]`

### A3.9 — Режим замка «через 5 минут» считает от разблокировки, а не от ухода в фон `[решение]`

(`startedCount → 0` в `AppLockCoordinator`) и считать от него.

### A3.13 — Смена папки автобэкапа: старое разрешение не освобождается

### A3.14 — I-21 «через ту же цепочку миграций» не реализован для data-миграций `[решение]`

`restorePayload` вставляет DTO старой версии напрямую, полагаясь на дефолты новых полей. Для
структурных миграций это эквивалентно; для data-миграций (как `MIGRATION_5_6` — посев категорий) — нет:
будущая миграция, преобразующая данные, не применится к восстановленному старому бэкапу. Либо
переформулировать I-21, либо восстанавливать старый бэкап во временную БД его версии и прогонять
миграции.

### A3.15 — CSV: без BOM, суммы — строки с символом валюты

`DATA/export/CsvExport.kt:49-55` пишет UTF-8 без BOM — Excel на Windows открывает кириллицу
«кракозябрами». Суммы — отформатированные строки («-1 234.56 ₽»), в таблице их не сложить. Добавить
BOM (или опцию), колонки «сумма» (plain `-1234.56`) и «валюта» (код) рядом с отформатированной.
