# Синхронизация между устройствами — проект

Статус: **согласован** (2026-10-10). Этап S0 — сделан; дальше по §9.

Цель: вносить и править данные с любого своего устройства — Poco F8 Pro (Android), Huawei MatePad 11.5
(HarmonyOS 4.x, ставит APK), MacBook M4, ThinkPad X1 Carbon — и видеть одно и то же везде.

Решения, принятые на входе:
* транспорт — **общая папка + Syncthing**; в самом приложении сети по-прежнему нет (I-24, ADR-013 остаются);
* сначала Android ↔ Android (телефон + планшет), настольные машины — следующим этапом;
* на MacBook/ThinkPad — **веб-интерфейс** (варианты — §8).

---

## 1. Как это выглядит для пользователя

1. На каждое устройство ставится **Syncthing** (Android: Syncthing-Fork из F-Droid или APK — работает и без
   Google-сервисов, т.е. на MatePad; macOS/Windows/Linux — официальная сборка). Одна общая папка, например
   `Corriente-sync`, расшарена между всеми устройствами. Syncthing передаёт файлы напрямую между устройствами
   (в локальной сети или через свои ретрансляторы, зашифровано), без облака и аккаунтов.
2. В Corriente: «Настройки → Синхронизация → Выбрать папку» (та же SAF-папка, что у автобэкапа, только другая) и
   имя устройства («Poco», «MatePad»).
3. Первое подключение (§6): на устройстве с данными — «Начать синхронизацию с этого устройства»; на остальных —
   «Подключиться» (данные подтянутся из папки).
4. Дальше — само: после каждой записи (с задержкой ~10 с), при открытии приложения и раз в 15 минут в фоне
   Corriente выкладывает свои изменения в папку и забирает чужие. Задержка «внёс на телефоне → видно на планшете»
   = задержка Syncthing (секунды в одной Wi-Fi сети, минуты через интернет).
5. Экран «Синхронизация» показывает: последние обмены, какие устройства видны, конфликты, которые разрешились не
   в пользу этого устройства (их можно просмотреть).

Почему не облако/свой сервер: сеть в приложении = ADR-013 отменяется, плюс логины, офлайн-очереди, сервер,
который надо держать. Syncthing даёт ту же связность снаружи приложения — Corriente работает только с файлами.

## 2. Модель: журнал изменений по строкам + «последний пишущий побеждает»

**Единица синхронизации — строка таблицы** (`account`, `category`, `txn`, `budget`, `recurrence`, `currency`,
`import_batch`, `import_alias`, синхронизируемые `app_setting`). Не «операции пользователя» (их десятки видов и
каждую пришлось бы переносить), а итоговое состояние строки.

* **Захват изменений — триггерами SQLite**, а не в репозиториях. Так ловится любая запись: ввод, импорт Monefy,
  слияние категорий, откат батча, повторяющиеся платежи, быстрый ввод из виджета. Триггер на
  INSERT/UPDATE/DELETE кладёт `(таблица, ключ)` в `sync_outbox`; содержимое строки берётся в момент выгрузки
  (несколько правок одной строки между выгрузками схлопываются в одну).
* **Версия строки — гибридные логические часы (HLC)**: `(время, счётчик, устройство)`. Не просто время: часы
  планшета могут отставать на минуты, а HLC гарантирует, что изменение, сделанное *после* того, как устройство
  увидело чужое, всегда старше его. Хранится в отдельной таблице `sync_row_meta (table, pk, hlc, device, deleted)` —
  сами таблицы данных не получают служебных столбцов.
* **Слияние — LWW (last-writer-wins) по строке**: побеждает версия с бо́льшим HLC, равенство — по id устройства.
  Результат не зависит от порядка, в котором устройства получили файлы: все сходятся к одному состоянию.
* **Удаление — физическое, как сейчас**, но в `sync_row_meta` остаётся запись `deleted = 1` с HLC (надгробие).
  Без неё удалённая на телефоне операция вернулась бы с планшета.
* **При применении чужих изменений триггеры молчат** (флаг `applying` в `sync_state`, проверяемый в `WHEN`
  триггера), иначе изменения бесконечно отражались бы обратно.

Почему не поля целиком (field-level) и не CRDT: операция — маленькая строка, одновременная правка *одной и той
же* операции на двух устройствах — редкость; цена простоты — в таком редком случае побеждает одна из правок
целиком, а проигравшая видна на экране «Синхронизация». Это осознанный компромисс.

## 3. Файлы в общей папке

```
Corriente-sync/
  devices/<device-id>.json          имя устройства, версия схемы, версия приложения, «видел до» по каждому устройству
  changes/<device-id>/<seq>.json    пачка изменений этого устройства (строки целиком + HLC + надгробия)
  snapshots/<device-id>-<hlc>.json  компактный снимок (§7)
```

* **Каждое устройство пишет только в свои файлы** → у Syncthing не бывает конфликтов записи (его
  `.sync-conflict`-файлы не возникают по построению).
* Запись — во временный файл + переименование: недописанный файл никто не прочитает.
* Каждый файл несёт **версию схемы**. Устройство со старым приложением файлы новой схемы не применяет и пишет
  «обновите приложение на этом устройстве» (как с бэкапами, I-21). Поэтому при обновлении схемы обновлять
  приложение нужно на всех устройствах.
* Формат — JSON тех же DTO, что у бэкапа (`BackupPayload`): суммы — целые минорные единицы, без локали (I-1, I-25).

## 4. Где LWW по строке недостаточно — и что делаем

| Ситуация | Что сломается без правила | Правило |
|---|---|---|
| Повторяющийся платёж срабатывает на обоих устройствах | Две одинаковые операции | **Детерминированный id** операции: `uuid(rule_id + дата)`. Оба устройства создают одну и ту же строку — сливаются в одну. |
| Один и тот же файл Monefy импортирован на двух устройствах | Нарушение `ux_txn_import_hash` | Не возникает: импорт — только на основном устройстве (§10). |
| Две новые категории с одинаковым именем на разных устройствах | Нарушение `ux_category_name_kind` | Считаются одной категорией: побеждает меньший id, проигравшая превращается в **перенаправление** (`category_redirect`), её операции и бюджеты переводятся на победителя. Правило детерминировано — все устройства придут к одному. |
| Слияние категорий на телефоне, а на планшете тем временем операция в старую категорию | Операция ссылается на удалённую категорию | То же перенаправление: слияние пишет `category_redirect(from → into)`, оно синхронизируется и применяется к опоздавшим операциям. |
| Удаление счёта/категории на одном устройстве, новая операция в нём на другом | Висячая ссылка | **Ссылка сильнее удаления**: если после применения на строку кто-то ссылается, удаление отменяется (строка восстанавливается из её последней версии). |
| Смена валюты счёта на одном устройстве, операция в старой валюте на другом | I-15/I-23: валюта операции ≠ валюта счёта | Смена валюты счёта, у которого после слияния есть операции, отклоняется (остаётся валюта, в которой есть операции); отметка в конфликтах. |
| Бюджет одной категории создан на обоих устройствах | Два бюджета | Как с категориями: дубликат по `(категория, валюта, период)` сливается, побеждает меньший id. |
| Настройки | Замок приложения/папка автобэкапа одного устройства переехали бы на другое | Синхронизируются только «общие» ключи `app_setting`; привязанные к устройству (`auto_backup.`, `app_lock.`, `recurrence.last_error.`, `sync.`, виджет) — нет. Тот же список, что у бэкапа (A2.16). |
| Типовые категории засеяны на каждом устройстве | Дубли | Уже решено: у засеянных категорий детерминированные id (`seed-exp-…`) — сольются. |

После применения каждой пачки чужих изменений запускается **проверка целостности** — та же, что у
восстановления бэкапа (`BackupRepository.validate`). Если что-то не сходится, применение откатывается целиком
(транзакция), пачка помечается «не применена» и на экране синхронизации появляется ошибка. Битые данные в БД не
попадают — так же, как сейчас с бэкапами.

## 5. Что меняется в инвариантах

* **I-24 — без изменений.** В приложении нет сети; синхронизация — чтение/запись файлов через SAF.
* **I-22 — переформулируется:** «Удаление данных — физическое; флагов `isDeleted` в таблицах данных нет. Для
  синхронизации удаление фиксируется надгробием в служебной `sync_row_meta`, данные удалённой строки не хранятся».
* **I-21/I-20** — миграция схемы 7 → 8 (служебные таблицы `sync_*`, `category_redirect`, триггеры) — явный
  `Migration` с тестом, как всегда. В бэкап служебные таблицы не входят (бэкап — это данные).
* **Новый I-26:** все устройства синхронизации обязаны сходиться к одному состоянию независимо от порядка получения
  файлов. Проверяется тестом «N устройств, случайные операции, случайный порядок обмена → одинаковые БД».
* **Новый I-27:** id строк, которые могут независимо возникнуть на нескольких устройствах (повторяющиеся платежи,
  импорт, засев) — детерминированные.

## 6. Первое подключение

* **Устройство с данными** (телефон): «Начать синхронизацию» → создаёт `device-id`, выгружает **базовый снимок**
  всех строк (иначе данные, появившиеся до включения синхронизации, никогда не попали бы в журнал).
* **Новое устройство** (планшет): «Подключиться» → если в его БД только засеянные категории — применяет снимок и
  журналы из папки. Если на нём уже есть свои операции — предупреждение и выбор: «Объединить» (LWW, возможны
  дубликаты счетов с одинаковым именем — их можно слить вручную) или «Заменить данными из папки» (с копией
  «до миграции», как при восстановлении бэкапа, A2.15).
* Перед первым применением чужих данных — автоматическая копия БД (уже есть механизм `pre-migration`).

## 7. Рост папки

Журналы растут. Раз в месяц (или по кнопке) устройство пишет свой снимок и удаляет собственные файлы
`changes/`, которые **все известные устройства уже применили** (по их `devices/*.json`, поле «видел до»).
Устройство, которое давно не появлялось (> 90 дней), перестаёт блокировать очистку; при возвращении оно
подключается заново через снимки. Надгробия старше 90 дней удаляются.

## 8. MacBook и ThinkPad: веб-интерфейс

Android-приложения на них не запускаются (macOS — никак; Windows — Microsoft закрыл подсистему Android), значит,
нужен отдельный клиент. Варианты веб-интерфейса:

**В1. Маленькое настольное приложение «Corriente Desktop», которое открывает интерфейс в браузере (рекомендую).**
Kotlin/JVM, один и тот же для macOS и Windows/Linux. Внутри — та же денежная логика (`:core:money` уже чистый
Kotlin/JVM, переиспользуется как есть) и тот же движок синхронизации; своя локальная SQLite-копия; читает/пишет ту
же папку Syncthing. Интерфейс — веб-страница на `http://127.0.0.1:<порт>`, открывается в любом браузере, включая
Safari. Слушает **только** локальный адрес (с другого компьютера сети не видно), сеть наружу не нужна.
* Плюсы: одна реализация денежных правил на Kotlin для телефона и десктопа — инварианты не дублируются; работает
  в любом браузере; иконка в трее/доке, автозапуск.
* Минусы: надо установить программу (JDK внутри пакета, ~60–80 МБ) и подготовить `:core:data` к работе вне
  Android (Room 2.7+ это умеет — нужно перевести модуль на Kotlin Multiplatform).

**В2. Одна HTML-страница без установки** (открывается в Chrome/Edge, работает с папкой Syncthing через File
System Access API). Плюсы: ничего не ставить. Минусы: **не работает в Safari** (на MacBook — только Chrome),
доступ к папке надо подтверждать, а денежную логику и проверки целостности пришлось бы переписать на
JavaScript — второй экземпляр правил, который рано или поздно разойдётся с первым. Не рекомендую.

**В3. Нативное окно (Compose Desktop) вместо браузера.** То же, что В1, но интерфейс — окно, а не вкладка;
часть экранов можно перенести с Android почти без изменений. Если «в браузере» не принципиально — это дешевле
В1 в поддержке.

Объём десктопа на первом шаге: ввод расхода/дохода/перевода, список операций с поиском, балансы по счетам, кольцо
месяца. Импорт Monefy, автобэкап, замок, виджет — только на Android.

## 10. Решения (2026-10-10)

1. **LWW по строке** — да.
2. **Десктоп** — вариант выбираем после S4.
3. **Импорт Monefy — только на основном устройстве** (на том, с которого начата синхронизация, — телефон). На
   остальных пункты импорта и отката импорта при включённой синхронизации недоступны (S3). Поэтому правило §4 про
   детерминированный id импортированных операций не нужно — строка таблицы оставлена как пояснение, почему.
4. Перед установкой на телефон сборки со схемой 8 (S1) — **полный экспорт JSON** на телефоне.
