### 1.3 Ivy Wallet — разбор

Что нашлось хорошего и напрямую полезного:

* **Готовый маппинг Monefy CSV.** `temp/legacy-code/.../csv/CSVMapper.kt:129`:
  ```
  monefy() = RowMapping(
      date = 0, dateOnlyFormat = "dd/MM/yyyy",
      account = 1, category = 2, amount = 3, accountCurrency = 4,
      // 5 = converted amount, 6 = converted currency
      title = 7,
      defaultTypeToExpense = true,  // тип определяется знаком суммы
  )
  ```
  То есть колонки Monefy: `date, account, category, amount, currency, converted amount, converted currency, description`,
  дата `dd/MM/yyyy`, тип операции — по знаку суммы. Это готовая экономия нескольких часов
  на реверс-инжиниринге формата (проверить на твоём файле всё равно надо — см. §7).
* Разделение виджетов: баланс на Glance, «быстрое добавление» на RemoteViews — рабочий пример обоих подходов.

Что там плохо и почему это не база для форка:

* **Деньги — `Double`.** `TransactionEntity.amount: Double`, `toAmount: Double?`
  (`shared/data/core/.../entity/TransactionEntity.kt`). Виджет держит баланс в `doublePreferencesKey`.
  Исправить это в форке = переписать модель, БД, все use-case'ы, все отчёты и всю запись/чтение —
  то есть почти весь проект.
* **Истории курсов нет по конструкции.** `ExchangeRateEntity` — это `primaryKeys = ["baseCurrency","currency"]`,
  одна строка на пару валют, без даты. Отчёт за март 2019 пересчитается по сегодняшнему курсу — молча.
* **Курсы хранятся относительно базовой валюты пользователя.** `SyncExchangeRatesUseCase` при синхронизации
  берёт EUR-курсы и **пересчитывает их в базовую валюту**. Смена базовой валюты = перезапись всей таблицы курсов.
  Это ровно та ошибка, которую я в §2.2 предлагаю не повторять.
* **Проект брошен в середине рефакторинга.** Новый `ExchangeUseCase.convert()` — это буквально
  `TODO("Not implemented")`, а рабочая логика живёт в модуле `temp/legacy-code`. Форкая это, ты
  наследуешь два параллельных недоделанных слоя. Для работы через AI-агента это худший из возможных входов:
  агент не сможет понять, какой из двух путей «настоящий».
* Мёртвые поля синхронизации (`isSynced`, `isDeleted`) с комментарием «нельзя удалить из-за обратной совместимости» —
  наглядный памятник преждевременному закладыванию на облако.

    commodity text NOT NULL,
    currency  text NOT NULL references currencies(code) ON DELETE CASCADE,

    source    text NOT NULL,

  подход «снимок в транзакции» (инвариант I-7).
* **Источники курсов**: Frankfurter (ECB), OpenExchangeRates (ключ), CoinApi (ключ) — `retrofit/ExchangeRateService.kt`.

### 1.8 ADR-001: форк, заимствование или с нуля

**Контекст.** Один разработчик, пишущий через AI-агентов. Требования: честная мультивалютность
с историческими курсами, виджет, импорт Monefy, офлайн. Ключевое ограничение — не столько часы,
сколько **объём кода, который агент должен удерживать в голове**, и **количество ручной отладки**.

**Варианты.**

**A. Форк Ivy Wallet.**
*Плюсы:* Kotlin/Compose/Room — стек, который ты и хотел; готовый импорт Monefy; два вида виджетов; красивый UI.
*Минусы:* деньги на `Double` пронизывают всё; истории курсов нет в принципе; проект брошен на середине
рефакторинга (два параллельных слоя, `TODO()` в новом коде); GPL-3.0 обязывает открывать твои изменения
**если ты распространяешь** приложение (для личного использования — не обязывает вообще).
*Оценка:* 90–160 ч. Из них 50+ — миграция `Double → Long` и введение историчности курсов, то есть
ты платишь за чужой UI переписыванием ядра. Плюс постоянная «дань»: каждый агентский промпт будет
натыкаться на legacy-модуль.

**B. Форк My Expenses.**
*Плюсы:* всё требуемое уже работает и работает правильно.
*Минусы:* 17k коммитов, Java+Kotlin, ContentProvider, флейворы, синхронизация — вырезать это дороже,
чем написать нужное. Агент физически не сможет держать этот проект в контексте: любое изменение
превращается в археологию.
*Оценка:* 60–120 ч только на «освоить и вычистить», и всё это время у тебя не будет ни одной новой строчки
собственной логики. Реалистичный итог — ты останешься с чужим приложением, которое побаиваешься трогать.

**C. С нуля + точечное заимствование.**
Заимствуем ровно четыре вещи (все — GPL-3.0, все — «идея/структура», не копипаста файлов):
1. маппинг колонок Monefy CSV (Ivy, `CSVMapper.kt:129`) — как спецификацию формата;
2. модель `Money(amountMinor: Long, currency)` (My Expenses) — как проверенный дизайн;
3. таблицу `prices` + приоритет источников (My Expenses) — как дизайн кэша курсов;
4. разделение «виджет-баланс читает снимок / виджет-кнопка запускает Activity» (Ivy) — как паттерн.
*Плюсы:* весь код написан под твои инварианты; объём — 6–8 тысяч строк, агент держит проект целиком;
нет чужого legacy; тесты пишутся сразу под инварианты.
*Минусы:* ты платишь UI-полировкой (первые версии будут страшнее Monefy) и тем, что сам себе
QA. И риск «не дойти до конца» выше, чем при форке.
*Оценка:* 70–115 ч, рабочее приложение для ручного учёта — на 25–40 часу.

**Выбор: C.**

Решающий аргумент не в часах (они сопоставимы), а в том, что ты просил минимум ручной отладки и минимум
абстракций, которые агенту трудно держать в голове. Форк даёт ровно обратное: чужие абстракции, которые
агент **обязан** удержать, но не может, потому что их в 10 раз больше, чем твоего кода. При работе через
агентов стоимость чтения чужого кода приближается к стоимости написания своего, а стоимость **отладки**
чужого — существенно выше.

**Последствия.**
* Ты берёшь на себя всё: миграции, бэкапы, edge-кейсы платформы. Отсюда §6 — этапы и инварианты.
* Лицензия твоего кода — на твоё усмотрение (я не копирую GPL-код построчно). Если решишь копировать
  файлы из Ivy/My Expenses буквально — весь проект придётся выпускать под GPL-3.0. Для личного,
  нераспространяемого приложения GPL вообще не накладывает обязательств: обязательства возникают
  **только при передаче копий** третьим лицам.
* Первые 2–3 месяца Monefy остаётся у тебя как эталон для сверки цифр. Не удаляй её и не выключай экспорт.

### 1.9 Почему не остаться на готовом (проверено на практике)

Первая редакция этого документа заканчивалась вопросом: «My Expenses покрывает ТЗ — может, просто
пользоваться им?». Вопрос закрыт эмпирически: **импорт CSV и автоматическая загрузка курсов
там за пейволлом** (`ContribFeature.CSV_IMPORT` → EXTENDED, `AUTOMATIC_FX_DOWNLOAD` → PROFESSIONAL).
Оба пункта — не украшения, а прямые требования №4 и №6 твоего ТЗ.

Варианты, оставшиеся у «готового» пути, и почему они хуже:
* **Купить лицензию** — снимает пейволл, но не снимает главного: чужой UX, 17k коммитов, невозможность
  править приложение под себя через агента. Если бы цель была «просто вести учёт», это был бы
  разумный выбор; но тогда и Monefy менять было незачем.
* **Форкнуть и убрать проверку лицензии** — GPL-3.0 это позволяет, но ты наследуешь поддержку
  огромной кодовой базы ради двух функций и вступаешь в неприятные отношения с автором,
  который этим живёт.
* **Написать своё** — ADR-001, вариант C.

**Решение принято: пишем своё.** Дальше документ только об этом.

## 2. Модель денег и валют

Это ядро. Всё остальное — обвязка вокруг него.

### 2.1 ADR-002: представление сумм

**Контекст.** RUB, UZS, USD. Суммы в UZS — крупные числа (обед ≈ 60 000 сум, зарплата — десятки миллионов).
Нужны точные суммы и отсутствие «плавающих копеек» в отчётах за годы.

**Варианты.**
1. `Double` — как в Ivy. Быстро, привычно, ломается тихо: `0.1 + 0.2 != 0.3`, суммы за год «разъезжаются»
   на копейки, сравнение балансов с банком превращается в расследование.
2. `BigDecimal` в БД (TEXT/REAL) — точно, но: медленно, аллокации, легко потерять scale, Room-конвертеры,
   агент будет путать `equals` и `compareTo` (классическая ловушка: `BigDecimal("1.0") != BigDecimal("1.00")`).
3. **`Long` в минорных единицах + код валюты**, `BigDecimal` только как транзитный тип при парсинге/конверсии.

**Выбор: 3.**

```kotlin
@JvmInline
value class Minor(val raw: Long)               // сумма в минорных единицах

data class Money(val amount: Minor, val currency: CurrencyCode) {
    operator fun plus(o: Money): Money {
        require(currency == o.currency) { "currency mismatch: $currency vs ${o.currency}" }
        return Money(Minor(Math.addExact(amount.raw, o.amount.raw)), currency)
    }
    operator fun minus(o: Money): Money { /* symmetric, Math.subtractExact */ }
    operator fun unaryMinus(): Money = Money(Minor(Math.negateExact(amount.raw)), currency)
}

@JvmInline
value class CurrencyCode(val code: String)     // ISO-4217, uppercase, валидируется при создании
```

**Границы.** `Long` = ±9.22e18. При scale=2 это ±9.2e16 в основных единицах.
Даже в сумах (самая «крупная» из твоих валют) годовой оборот в 500 млн сум = 5e10 минорных единиц —
запас в 8 порядков. Переполнение возможно только при агрегировании миллиардов строк или при ошибке
в коде — и именно поэтому используется `Math.addExact`, который **падает**, а не молча переполняется
(инвариант I-3). Падение в тесте лучше, чем отрицательный баланс в отчёте.

**Про scale валюты.** Хранится в таблице `currency` (`minor_units`), не в коде. RUB=2, USD=2, UZS=2
формально по ISO-4217. Но тийины в Узбекистане не ходят: предлагаю различать
`minor_units` (для хранения, всегда по ISO) и `display_scale` (сколько знаков показывать; для UZS — 0).
Тогда ввод «60000» в UZS = 6 000 000 минорных единиц, а показывается «60 000». Хранение остаётся
универсальным, а UI — человеческим.
**ВОПРОС 6** (см. §7): согласен на такое разделение или хочешь UZS с `minor_units=0`?
Второе проще, но необратимо: если понадобятся тийины/копейки, потребуется миграция всех сумм.

**Последствия.**
* Любое место, где деньги превращаются в `Double` (графики, форматирование, JSON), — это граница,
  которую нужно явно контролировать. Ставим Detekt-правило/ручной чек-лист: `Double` в пакетах
  `money`, `data`, `domain` запрещён (инвариант I-1).
* Все арифметические операции — только между одинаковыми валютами. Складывать RUB и UZS без явной
  конверсии код не должен уметь **в принципе** — на уровне типов (инвариант I-2).

### 2.2 ADR-003: как хранится курс

**Контекст.** Нужны курсы для отчётов в базовой валюте и для переводов. Базовая валюта может меняться
(сегодня RUB, через год UZS).

**Варианты.**
1. Курсы к базовой валюте пользователя (Ivy). Смена базовой валюты → пересчёт/перезапись всей таблицы,
   накопление ошибок округления, потеря исходных данных провайдера.
2. Курсы «каждая пара к каждой» — комбинаторный взрыв (n² строк на дату), лишние данные.
3. **Курсы к фиксированному pivot (USD), кросс-курсы вычисляются на лету.**

**Выбор: 3.** Pivot = USD, зафиксирован на уровне БД и не зависит от настроек пользователя.

```
rate(A → B, date) = rate(A → USD, date) / rate(B → USD, date)
```

Почему USD, а не EUR: см. §2.6 — источник, который покрывает UZS и RUB, отдаёт данные с USD-базой,
и для твоих валют USD — более «ликвидный» pivot (RUB/USD и UZS/USD котируются напрямую, RUB/EUR — нет).

**Формат хранения курса.** `TEXT`, каноническая десятичная строка, минимум 12 значащих цифр,
парсится в `BigDecimal`. Не `Double` (см. I-1), не `Long` со скрытым множителем (агент рано или поздно
перепутает `e9` и `e12`, и это будет тихая ошибка на четвёртом знаке).

```kotlin
/** 1 единица [currency] стоит [rateToPivot] единиц PIVOT (USD) на дату [date]. */
data class FxRate(
    val currency: CurrencyCode,
    val date: LocalDate,
    val rateToPivot: BigDecimal,   // TEXT в БД
    val source: RateSource,        // MANUAL | PROVIDER | CARRIED_FORWARD | IMPORTED | DERIVED
)
```

**Направление — единственное и жёсткое** (инвариант I-5): «1 единица валюты X = R единиц USD».
Обратное направление не хранится никогда, только вычисляется. Это убирает целый класс ошибок
«курс перевёрнут», который в самодельных трекерах встречается чаще всего.

**Округление.** Конверсия — ровно одна точка в коде:

```kotlin
fun convert(m: Money, to: CurrencyCode, rf: RateAt): Money {
    val amountMajor = BigDecimal(m.amount.raw).movePointLeft(scaleOf(m.currency))
    val result = amountMajor
        .multiply(rf.rateToPivot(m.currency), MathContext(24, RoundingMode.HALF_UP))
        .divide(rf.rateToPivot(to),           MathContext(24, RoundingMode.HALF_UP))
    return Money(Minor(result.movePointRight(scaleOf(to))
        .setScale(0, RoundingMode.HALF_UP).longValueExact()), to)
}
```
Округление до минорных единиц происходит **один раз, в самом конце** (инвариант I-4). Промежуточные
результаты не округляются никогда — иначе сумма 300 конвертированных транзакций разъедется с
конвертацией их суммы.

**Последствия.**
* Смена базовой валюты — это изменение одной строки в настройках, ноль изменений данных.
* Кросс-курс UZS→RUB имеет двойную ошибку округления (через USD). При 24 знаках точности в
  промежуточных вычислениях это ниже уровня минорной единицы — неважно.
* Если когда-нибудь понадобится валюта, которой нет у провайдера в паре с USD, её курс придётся
  вводить руками — и это нормально, механизм `MANUAL` для этого и есть.

### 2.3 ADR-004: исторические курсы против текущих

Самый спорный вопрос из всех, поэтому разбираю подробно.

**Контекст.** Отчёт «расходы за март 2024» в базовой валюте RUB. Часть трат была в UZS.
По какому курсу их показать: по курсу марта 2024 или по сегодняшнему?

**Вариант A: исторические курсы (по дате операции).**
* Отчёт за март 2024 **никогда не меняется**. Открыл его сегодня, через год — одни и те же цифры.
* Отвечает на вопрос «сколько я тогда потратил» в терминах тогдашних денег. Это то, как считает бухгалтерия,
  и то, что интуитивно ожидается от фразы «я потратил в марте 250 тысяч».
* Требует истории курсов и снимка в транзакции. Требует ответа на вопрос «а если курса на ту дату нет».
* Побочный эффект: сумма расходов за 12 месяцев ≠ то, во что эти расходы «оцениваются» сегодня.

**Вариант B: текущий курс для всего.**
* Проще: одна таблица «последний курс», как в Ivy.
* Отвечает на вопрос «сколько мои прошлые траты стоят в сегодняшних деньгах». Изредка полезно.
* **Отчёт за март 2024 меняется каждый день.** При падении рубля на 20% «расходы марта» вырастают
  на 20% без единой новой транзакции. Сравнение месяцев между собой становится бессмысленным:
  ты сравниваешь не траты, а курс.
* Для UZS/RUB на горизонте «несколько лет» это не теоретическая проблема: курсы двигались десятками процентов.

**Выбор: A для потоков, B для запасов.** Это не компромисс, а точное разделение сущностей:

| Что | Курс | Почему |
|---|---|---|
| Доходы/расходы за период, отчёты по категориям, бюджеты | **Исторический** (снимок на дату операции) | Прошлое не должно меняться |
| Текущий баланс счёта в его валюте | Курс не нужен | — |
| Сводный баланс/капитал «сколько у меня всего сейчас» | **Текущий** (последний известный) | Вопрос о сегодняшней стоимости активов |
| Баланс на дату в прошлом («сколько было на 01.01.2025») | **Текущий на ту дату** | Тот же вопрос, но на прошлую дату |

**Последствия — и вот главное, что нужно понять заранее.** При таком разделении
«капитал вырос на X» **не равно** «доходы − расходы». Разница — переоценка валютных остатков:

```
Δкапитал(в базовой) = доходы(ист.) − расходы(ист.) + переоценка_FX
```

Это не баг и не расхождение округлений, это природа мультивалютного учёта. Приложение обязано
показывать член `переоценка_FX` **отдельной строкой** (инвариант I-13), иначе ты будешь регулярно
искать «пропавшие деньги». Ни Monefy, ни Ivy этого не делают — и именно поэтому в них сводные цифры
не сходятся с интуицией.

**Что даём в UI:** переключатель на экране отчёта «курсы: на дату операции / текущие»,
с умолчанием «на дату операции». My Expenses пришёл ровно к этому (`pref_dynamic_exchange_rates_*`) —
считаю это подтверждением, что умолчание должно быть, а выбор — оставаться.

### 2.4 ADR-005: перевод между счетами в разных валютах

**Контекст.** Перевожу 1 000 000 UZS со счёта UZS на счёт RUB, приходит 6 900 RUB.
Курсовая разница должна быть зафиксирована и не должна попадать в расходы.

**Варианты.**
1. **Две транзакции** (расход на счёте-источнике + доход на счёте-приёмнике), связанные `transfer_group_id`.
   Классика двойной записи. Минус: возможны «половинки» — если запись второй строки упала, БД
   в противоречивом состоянии; каждый отчёт обязан помнить, что эти строки надо исключать; удаление,
   редактирование и импорт усложняются вдвое.
2. **Одна транзакция с двумя суммами** (`from_account, from_amount, to_account, to_amount`).
   Так сделано и в Ivy (`toAccountId`/`toAmount`), и в My Expenses.
3. Три записи: две ноги + отдельная проводка «курсовая разница» (как в бухгалтерии).
   Честно, но требует служебного счёта «FX P&L» и понимания двойной записи в UI.

**Выбор: 2.**

```kotlin
// одна строка в таблице transactions, kind = TRANSFER
data class Transfer(
    val fromAccount: AccountId, val fromAmount: Money,   // 1 000 000 UZS
    val toAccount:   AccountId, val toAmount:   Money,   //     6 900 RUB
    val date: LocalDate,
    // снимки курсов обеих валют к USD на дату операции:
    val fromRateToPivot: BigDecimal, val toRateToPivot: BigDecimal,
)
```

**Где живёт курсовая разница.** Нигде — она **вычисляется** (инвариант I-12):

```
факт_курс      = to_amount / from_amount                      (неявный курс сделки)
рыночный_курс  = rate(from→to, date)                          (из снимков)
разница(в базовой) = base(to_amount, снимок) − base(from_amount, снимок)
```

Хранить её отдельным полем — значит завести второй источник истины, который рассинхронизируется
при любом редактировании транзакции. Если по производительности отчётов понадобится — материализуем
как denormalized-колонку с пересчётом в той же транзакции БД, но **только** как кэш (инвариант I-9).

`разница` — это ровно те деньги, которые ты потерял (или выиграл) на конвертации относительно
рыночного курса дня: комиссия обменника, спред, разница между курсом банка и ЦБ. Это интересная
и полезная цифра — предлагаю отдельный маленький отчёт «потери на конвертациях за период».

**Последствия.**
* Перевод атомарен по построению: «половинок» не бывает (инвариант I-10).
* Переводы исключаются из доходов/расходов одним условием `kind != TRANSFER` (инвариант I-11) —
  это одна строка в каждом запросе, а не сложный self-join, как в варианте 1.
* Перевод внутри одной валюты — частный случай: `from.currency == to.currency`, разница = 0.
* Ограничение: одна строка не описывает перевод «1 → много счетов». Тебе это не нужно; если понадобится —
  это отдельная сущность, а не переделка этой.

### 2.5 ADR-006: источник курсов, кэш и поведение без сети

**Контекст.** Нужны дневные курсы RUB, UZS, USD (и расширяемо). Приложение офлайн-first.
Нужны **исторические** курсы за несколько лет назад — для импорта истории из Monefy.

**Найденное ограничение, важное именно для твоих валют.**
ECB (и построенный на нём бесплатный Frankfurter, который использует My Expenses) **не подходит**:
ЕЦБ прекратил публикацию референсного курса рубля **1 марта 2022 года** и не возобновил;
узбекского сума в списке ЕЦБ нет вообще. То есть самый популярный бесплатный источник
закрывает у тебя ровно одну валюту из трёх.

**Варианты.**
1. `@fawazahmed0/currency-api` (jsDelivr + Cloudflare-зеркало, CC0, 200+ валют включая RUB и UZS,
   без ключа, без rate-limit, дневные срезы адресуются датой:
   `.../@fawazahmed0/currency-api@YYYY-MM-DD/v1/currencies/usd.min.json`). Это то, чем в итоге
   пользуется Ivy (`RemoteExchangeRatesDataSourceImpl` — четыре зеркала подряд).
   Минус: неофициальный источник, живёт волей одного мейнтейнера; **глубину истории надо проверить**
   (см. §7, ВОПРОС 2) — я не смог её проверить из этой среды, egress-прокси блокирует CDN.
2. ЦБ РФ (`cbr.ru`, `XML_daily.asp?date_req=dd/mm/yyyy`) — официальный, есть архив на годы назад,
   есть UZS. База — RUB. Для тебя как для человека, живущего в рублёвой и сумовой реальности,
   это самый «правильный» по смыслу курс.
3. ЦБ Узбекистана (`cbu.uz`, архив в JSON/CSV) — официальный для UZS.
4. Платные (OpenExchangeRates и т.п.) — ключ, лимиты, регистрация. Для личного приложения — лишнее.

**Выбор: (1) как основной провайдер, (2)/(3) как опциональные альтернативные источники,
плюс всегда доступный ручной ввод.** Архитектурно важно, что источник — это **данные**
(строка `source` в таблице курсов), а не ветка в коде: добавление ЦБ РФ позже = новый класс на 40 строк
и новая строка в enum, без изменения схемы и логики отчётов.

**Формат кэша.**

```sql
CREATE TABLE fx_rate (
  currency  TEXT NOT NULL,          -- 'UZS'
  date      TEXT NOT NULL,          -- 'YYYY-MM-DD', дата курса
  rate      TEXT NOT NULL,          -- десятичная строка, 1 currency = rate USD
  source    TEXT NOT NULL,          -- MANUAL | FAWAZ | CBR | CBU | IMPORTED | CARRIED_FORWARD
  fetched_at INTEGER NOT NULL,
  PRIMARY KEY (currency, date, source)
);
```

Кэш **append-only**: автосинхронизация никогда не перезаписывает строку с `source='MANUAL'`
(инвариант I-18). Выбор действующего курса — по приоритету источников, как `prioritized_prices`
в My Expenses: `MANUAL > CBR/CBU > FAWAZ > CARRIED_FORWARD`.

**Поведение при отсутствии сети:** ничего не происходит. Все операции работают на кэше;
WorkManager с `NetworkType.CONNECTED` дотянет курсы, когда сеть появится. Ежедневная синхронизация —
одна задача, докачивающая пропущенные дни (не только «сегодня», иначе после недели без сети
в истории останутся дыры).

**Поведение при отсутствии курса на нужную дату** (это самое важное место, где самодельные трекеры врут):

| Ситуация | Поведение |
|---|---|
| Курс на дату есть | Берём его |
| Курса на дату нет, но есть более ранний | Берём последний известный ≤ даты, помечаем `CARRIED_FORWARD` (выходные, праздники — нормальный случай) |
| Курса нет вообще (дата раньше начала истории; экзотическая валюта) | **`RateMissing`** — явное состояние. Сумма показывается как «— н/д», отчёт помечается как неполный со списком проблемных дат, пользователю предлагается ввести курс руками |
| Курс есть, но «протухший» (например, старше 30 дней при показе текущего капитала) | Показываем с пометкой «курс от 12.03», не молчим |

Категорически запрещено (инвариант I-16): подставлять `1.0`, `0`, курс другой даты без пометки,
или молча пропускать транзакцию в агрегате. Лучше показать «н/д», чем красивое неверное число —
на этом ломается доверие ко всему приложению.

**Отдельно про импорт истории из Monefy.** У тебя несколько лет истории; глубина бесплатного
источника под вопросом. Три источника курсов для старых транзакций, по убыванию приоритета:
1. **Из самого CSV**: у Monefy есть колонки `amount/currency` и `converted amount/converted currency` —
   их отношение даёт **фактический курс, который использовала Monefy** на момент операции.
   Это лучший источник: он согласован с цифрами, которые ты видел все эти годы (`source='IMPORTED'`).
2. Архив провайдера/ЦБ РФ на дату, если доступен.
3. `CARRIED_FORWARD` от ближайшей известной даты + явный список «плохих» периодов в отчёте об импорте.

### 2.6 Инварианты

Это чек-лист, по которому можно проверять любой сгенерированный агентом код. Нарушение любого
из пунктов — баг, даже если тесты зелёные. Держать в `docs/INVARIANTS.md` и вставлять в промпты агента.

**Деньги**
* **I-1.** Деньги нигде не представлены `Double`/`Float`: ни в БД, ни в domain, ни в DTO, ни в UI-state,
  ни в снимке для виджета. `BigDecimal` допустим только как транзитный тип внутри парсинга и конверсии.
* **I-2.** Арифметика над `Money` допустима только при совпадении валют; несовпадение = исключение,
  а не приведение.
* **I-3.** Сложение/вычитание/отрицание — через `Math.addExact/subtractExact/negateExact`.
  Переполнение приводит к падению, а не к неверному числу.
* **I-4.** Округление до минорных единиц происходит ровно один раз — на выходе конверсии, `HALF_UP`.
  Промежуточные вычисления не округляются.
* **I-5.** Курс хранится в единственном направлении: «1 единица валюты X = R единиц PIVOT». Обратные
  и кросс-курсы только вычисляются.
* **I-6.** PIVOT (USD) фиксирован в схеме и не зависит от базовой валюты пользователя. Смена базовой
  валюты не изменяет ни одной строки данных.
* **I-7.** Каждая транзакция в валюте, отличной от PIVOT, хранит снимок курса на дату операции и его
  источник. Снимок иммутабелен: он меняется только явной командой «пересчитать по актуальным курсам»,
  и такая команда логируется.
* **I-8.** Отчёты о потоках (доходы/расходы за период) считаются по снимкам. Балансы и капитал — по
  последним известным курсам. Одно число никогда не смешивает два режима.
* **I-9.** Сумма в базовой валюте — всегда производная от `(amount, currency, rate)`. Если она где-то
  материализована, это кэш, пересчитываемый в той же транзакции БД, что и источник.
* **I-10.** Перевод — ровно одна строка. Состояния «есть только одна половина перевода» не существует.
* **I-11.** Транзакции с `kind = TRANSFER` не входят ни в доходы, ни в расходы, ни в отчёты по категориям.
* **I-12.** Курсовая разница вычисляется из снимков, не вводится пользователем и не хранится как
  независимое значение.
* **I-13.** Приложение умеет показать `Δкапитал = доходы − расходы + переоценка_FX` с явным членом
  переоценки. Расхождение никогда не прячется.
* **I-14.** Валюта — строка в таблице `currency`, а не enum в коде. Добавление валюты = INSERT,
  без миграции схемы и без релиза приложения.
* **I-15.** Валюта транзакции всегда равна валюте счёта. Покупка в чужой валюте с рублёвой карты
  записывается в рублях (как её видит банк); реальная конвертация моделируется переводом.

**Курсы и данные**
* **I-16.** Отсутствие курса — явное состояние `RateMissing`. Никогда не подставляется `1.0`, `0` или
  курс другой даты без пометки. Неполный отчёт помечен как неполный.
* **I-17.** Если курс взят с более ранней даты, это зафиксировано в `source = CARRIED_FORWARD` и видно в UI.
* **I-18.** Кэш курсов append-only по `(currency, date, source)`. Ручной курс (`MANUAL`) имеет высший
  приоритет и никогда не перезаписывается автосинхронизацией.
* **I-19.** Импорт идемпотентен: повторный импорт того же файла не создаёт дублей; каждый импорт —
  это `import_batch`, удаляемый целиком одной операцией.
* **I-20.** Никакого `fallbackToDestructiveMigration()`. Каждая миграция — явный `Migration`-объект
  с тестом. Перед применением миграции автоматически создаётся копия файла БД.
* **I-21.** Бэкап содержит версию схемы и восстанавливает состояние полностью, включая курсы, снимки
  и справочники. Восстановление из бэкапа более старой версии проходит через ту же цепочку миграций.
* **I-22.** Удаление данных — физическое. Флагов `isDeleted` нет (они нужны только для синхронизации,
  которой нет; см. Ivy как пример того, во что это вырождается).

## 3. Схема данных

### 3.1 ADR-007: идентификаторы — UUID, а не autoincrement

**Контекст.** Синхронизации нет и не будет. Но есть бэкапы, восстановление на новом телефоне и
импорт партиями.

**Варианты.** `INTEGER PRIMARY KEY AUTOINCREMENT` (проще, компактнее, читаемее в отладке) против
`TEXT` UUID.

**Выбор: UUID (TEXT, canonical lowercase).** Обоснование — **не** «на будущее для синхронизации»
(это было бы ровно то преждевременное усложнение, о котором ты предупредил), а три сегодняшние задачи:
1. восстановление из бэкапа в чистую установку должно сохранять идентичность записей, чтобы повторное
   восстановление того же файла было идемпотентным (I-19/I-21);
2. импорт партиями требует стабильных ключей для отката батча;
3. при слиянии двух бэкапов (потерял телефон, есть бэкап недельной давности + свежий экспорт)
   автоинкрементные ID гарантированно конфликтуют, UUID — нет.

**Последствия.** Индексы чуть больше, `JOIN`-ы чуть медленнее — на 50–100 тысячах строк это
не измеряется. В отладке ID менее читаемы: компенсируется тем, что в UI и логах показываем
префикс из 8 символов.

### 3.2 Таблицы

```sql
-- Справочник валют. Добавление валюты = INSERT (I-14).
CREATE TABLE currency (
  code          TEXT PRIMARY KEY,        -- 'RUB', 'UZS', 'USD'
  minor_units   INTEGER NOT NULL,        -- ISO-4217 exponent: 2
  display_scale INTEGER NOT NULL,        -- сколько знаков показывать: RUB=2, UZS=0
  symbol        TEXT NOT NULL,           -- '₽', 'сум', '$'
  display_order INTEGER NOT NULL DEFAULT 0,
  is_archived   INTEGER NOT NULL DEFAULT 0
);

CREATE TABLE account (
  id            TEXT PRIMARY KEY,
  name          TEXT NOT NULL,
  currency_code TEXT NOT NULL REFERENCES currency(code),
  kind          TEXT NOT NULL,           -- CASH | CARD | SAVINGS | DEBT
  opening_balance_minor INTEGER NOT NULL DEFAULT 0,
  color         INTEGER NOT NULL,
  icon          TEXT,
  display_order INTEGER NOT NULL DEFAULT 0,
  is_archived   INTEGER NOT NULL DEFAULT 0,
  include_in_total INTEGER NOT NULL DEFAULT 1
);

CREATE TABLE category (
  id            TEXT PRIMARY KEY,
  name          TEXT NOT NULL,
  kind          TEXT NOT NULL,           -- EXPENSE | INCOME
  parent_id     TEXT REFERENCES category(id),   -- одна степень вложенности, не дерево
  color         INTEGER NOT NULL,
  icon          TEXT,
  origin        TEXT NOT NULL DEFAULT 'USER',   -- USER | IMPORT  (см. §3.5)
  display_order INTEGER NOT NULL DEFAULT 0,
  is_archived   INTEGER NOT NULL DEFAULT 0
);
CREATE UNIQUE INDEX ux_category_name_kind ON category(name, kind) WHERE is_archived = 0;

-- Ядро. Одна строка на операцию, включая переводы (I-10).
CREATE TABLE txn (
  id              TEXT PRIMARY KEY,
  kind            TEXT NOT NULL,          -- EXPENSE | INCOME | TRANSFER
  date            TEXT NOT NULL,          -- 'YYYY-MM-DD', локальная дата операции
  created_at      INTEGER NOT NULL,       -- epoch millis, для сортировки внутри дня
  updated_at      INTEGER NOT NULL,

  account_id      TEXT NOT NULL REFERENCES account(id),
  amount_minor    INTEGER NOT NULL,       -- всегда > 0; знак определяется kind (I-1)
  currency_code   TEXT NOT NULL REFERENCES currency(code),  -- == account.currency_code (I-15)
  rate_to_pivot   TEXT NOT NULL,          -- снимок курса на дату операции (I-7)
  rate_source     TEXT NOT NULL,          -- откуда снимок

  -- только для kind = TRANSFER:
  to_account_id   TEXT REFERENCES account(id),
  to_amount_minor INTEGER,
  to_currency_code TEXT REFERENCES currency(code),
  to_rate_to_pivot TEXT,

  category_id     TEXT REFERENCES category(id),   -- NULL для TRANSFER
  note            TEXT,
  import_batch_id TEXT REFERENCES import_batch(id),
  import_hash     TEXT,                   -- натуральный ключ строки CSV (I-19)

  CHECK (amount_minor > 0),
  CHECK ((kind = 'TRANSFER') = (to_account_id IS NOT NULL)),
  CHECK ((kind = 'TRANSFER') = (category_id IS NULL))
);

CREATE INDEX ix_txn_date            ON txn(date);
CREATE INDEX ix_txn_account_date    ON txn(account_id, date);
CREATE INDEX ix_txn_category_date   ON txn(category_id, date) WHERE category_id IS NOT NULL;
CREATE INDEX ix_txn_to_account_date ON txn(to_account_id, date) WHERE to_account_id IS NOT NULL;
CREATE UNIQUE INDEX ux_txn_import_hash ON txn(import_hash) WHERE import_hash IS NOT NULL;

CREATE TABLE fx_rate (            -- см. §2.5
  currency TEXT NOT NULL REFERENCES currency(code),
  date     TEXT NOT NULL,
  rate     TEXT NOT NULL,
  source   TEXT NOT NULL,
  fetched_at INTEGER NOT NULL,
  PRIMARY KEY (currency, date, source)
);
CREATE INDEX ix_fx_rate_lookup ON fx_rate(currency, date DESC);

CREATE TABLE import_batch (
  id          TEXT PRIMARY KEY,
  source_app  TEXT NOT NULL,        -- 'MONEFY'
  file_name   TEXT NOT NULL,
  imported_at INTEGER NOT NULL,
  row_count   INTEGER NOT NULL,
  report_json TEXT NOT NULL         -- что не распозналось, какие категории созданы, где нет курсов
);

CREATE TABLE app_setting (          -- key-value, чтобы не плодить миграций на каждую настройку
  key TEXT PRIMARY KEY,
  value TEXT NOT NULL
);                                  -- base_currency, rate_provider, report_rate_mode, ...
```

**Про `amount_minor > 0` и знак.** Знак определяется `kind`, а не значением. Причина: `-500` в
поле «доход» — состояние, которое агент рано или поздно создаст, и оно тихо сломает агрегаты.
`CHECK` ловит это на уровне SQLite.

**Про снимок в каждой транзакции.** Да, для транзакций в базовой валюте это избыточно
(`rate_to_pivot` там равен курсу базовой валюты). Зато нет ветвлений «если валюта базовая, то...» —
одинаковый путь для всех записей, что важнее экономии байт (и заметно снижает шанс,
что агент напишет неверную ветку).

**Чего в схеме нет намеренно:** таблиц синхронизации, флагов `is_deleted`, `user_id`, `device_id`,
`server_revision`, тегов, вложений, повторяющихся платежей, бюджетов. Первые пять — это ровно то
преждевременное усложнение под «облако в будущем», от которого ты просил воздержаться,
а Ivy — живой памятник тому, во что оно превращается. Последние четыре — фичи, которые
добавляются потом отдельными таблицами, ничего не ломая.

### 3.3 ADR-008: стратегия миграций

**Выбор:** Room с `exportSchema = true`, схемы (`schemas/*.json`) **коммитятся в репозиторий**,
каждая миграция — явный объект `Migration(n, n+1)`, автомиграции Room — только для тривиальных
случаев (добавление nullable-колонки), и всегда с тестом.

Правила (они же I-20):
1. `fallbackToDestructiveMigration()` запрещён в любом виде и в любом билд-типе. Один такой вызов
   в релизе — и несколько лет истории исчезают молча.
2. На каждую миграцию — тест через `MigrationTestHelper`: создать БД версии N, наполнить, мигрировать,
   проверить данные. Это единственный вид теста, который реально спасает данные,
   и он идеально ложится на работу с агентом: тест пишется тем же промптом, что и миграция.
3. Перед применением миграции — копия файла БД в `files/backup/pre_migration_v{N}.db`, хранить последние 3.
4. Изменения, которые не требуют миграции вообще (новая валюта, новая категория, новая настройка), —
   это INSERT в `currency` / `category` / `app_setting`. Схема спроектирована так, чтобы
   такие изменения были данными (I-14).

### 3.4 Как схема переживает новую валюту

`INSERT INTO currency(...)` + подтягивание курсов провайдером. Ноль изменений кода, ноль миграций,
ноль релизов. Единственное, что нужно проверить: провайдер знает этот код валюты, иначе
курсы вводятся вручную (`source='MANUAL'`) — механизм уже есть.

Ограничение: удалять валюту, на которую ссылаются счета, нельзя — только архивировать
(`is_archived = 1`). Это защищает историю.

### 3.5 Импорт истории и незнакомые категории

Основная сложность импорта не в парсинге, а в том, что справочники Monefy и твои не совпадут.

**Механика.**
1. **Dry-run обязателен.** Импортёр сначала строит отчёт: сколько строк, какие счета/категории/валюты
   встретились, каких нет в справочниках, за какие даты нет курсов, сколько строк не распарсилось.
   Пользователь видит это **до** записи в БД.
2. **Незнакомые категории создаются автоматически** с `origin='IMPORT'` — не отбрасываются и не
   сваливаются в «Прочее». Потеря категоризации за несколько лет необратима; лишняя категория —
   косметика, которую можно почистить потом.
3. **Таблица алиасов** для ручного маппинга «категория Monefy → моя категория»:
   ```sql
   CREATE TABLE import_alias (
     source_app TEXT NOT NULL, kind TEXT NOT NULL,   -- CATEGORY | ACCOUNT | CURRENCY
     source_value TEXT NOT NULL, target_id TEXT NOT NULL,
     PRIMARY KEY (source_app, kind, source_value)
   );
   ```
   Алиасы применяются при импорте и переиспользуются при повторных импортах.
4. **Слияние категорий** — отдельная операция «объединить A в B» (UPDATE txn SET category_id, DELETE A),
   доступная после импорта. Так разбор справочника не блокирует сам импорт.
5. **Идемпотентность.** `import_hash = sha256(source_app | date | account | category | amount | currency | note)`.
   При повторном импорте строки с уже существующим хэшем пропускаются и попадают в отчёт как «дубликаты».
   Если в истории есть **две легитимно одинаковые** операции в один день (два кофе по 15 000 сум) —
   это ложное срабатывание, поэтому в хэш добавляется порядковый номер повторения внутри дня.
6. **Откат батча целиком** — `DELETE FROM txn WHERE import_batch_id = ?`, плюс удаление категорий
   с `origin='IMPORT'`, на которые больше нет ссылок. Первые попытки импорта заведомо будут
   неудачными; возможность откатить их одной кнопкой превращает страшную операцию в рутинную.
7. **Курсы из CSV** (см. §2.5): отношение `converted amount / amount` пишется в `fx_rate`
   c `source='IMPORTED'` и служит снимком для этих транзакций.

**Формат разобран на реальном экспорте** — полная спецификация в
[`docs/MONEFY_IMPORT.md`](MONEFY_IMPORT.md), синтетический приёмочный файл — в
`testdata/monefy_sample.csv`. Кратко о том, что подтвердилось и что оказалось не так,
как предполагалось:

* Переводы приезжают **двумя строками** с псевдокатегориями `To 'Счёт'` / `From 'Счёт'`;
  склеиваются по дате и равенству модуля `converted amount`.
* Начальные остатки — тоже псевдокатегория (`Initial balance 'Счёт'`), в доходы не идут.
* Запятая — разделитель **тысяч**, точка — десятичный. Локале-зависимый парсер уменьшит
  суммы в 1000 раз молча и правдоподобно — это главный риск импорта.
* Колонки 5 и 7 обе называются `currency`: разбирать только по индексам.
* Заметки в экспорте пусты во всех строках — переносить нечего.
* В данных есть строки с исторически неверной валютой (Monefy подставляет **текущую** валюту счёта
  к старым суммам). Такие строки идут в `NEEDS_REVIEW`, а не импортируются «как есть».

## 4. Виджет

### 4.1 ADR-009: Glance против RemoteViews

**Контекст.** Нужен виджет: текущий баланс + быстрое добавление траты. Разработка идёт через
AI-агента, то есть цена «ещё одного языка описания UI» (XML-лэйауты + `R.id.*` + ручная привязка)
выше обычной: агент должен синхронно править три файла и не имеет обратной связи от компилятора
по поводу того, что `R.id.tvBalance` — это именно тот `TextView`.

**Варианты.**
1. **RemoteViews** — как в My Expenses и MMEX. Ниже уровень, полный контроль, ноль зависимостей,
   работает на любых версиях Android. XML-лэйауты + императивные `setTextViewText(R.id..., ...)`.
2. **Glance** (`androidx.glance:glance-appwidget`, stable **1.1.1** от 16.10.2024; 1.2.0-rc01 — декабрь 2025;
   1.3.0-alpha02 — июль 2026). Compose-подобный DSL, который компилируется в те же RemoteViews.
3. Гибрид, как в Ivy: баланс — Glance, кнопки — RemoteViews.

**Выбор: Glance** (вариант 2), целиком.

Обоснование:
* Один язык (Kotlin) и один способ описания UI на весь проект. Для агентской разработки это
  главный фактор: правка виджета не требует переключения парадигмы и синхронизации XML с кодом.
* Состояние виджета — `PreferencesGlanceStateDefinition` (DataStore), то есть готовый и типизированный
  механизм снимка данных. В RemoteViews это пишется руками.
* Стабильная версия существует два года, API устоялось, Ivy на нём держал боевой виджет баланса.
* RemoteViews никуда не исчезает: Glance генерирует их под капотом, и все платформенные ограничения
  всё равно придётся уважать — но не придётся их **кодировать**.

Чем платишь:
* Зависимость на 1.1.1 из октября 2024 — обновления редки; часть новых возможностей (например,
  тонкости работы с размерами) только в alpha 1.3.
* Диагностика хуже: ошибка в Glance-композиции обычно даёт «Загрузка…» или пустой виджет,
  а не понятный стектрейс. Отсюда правило: **вся логика — вне композиции**, в снимке (см. §4.2),
  композиция только рисует готовые строки.
* Чуть больший APK и чуть более медленный первый рендер. Неважно.

### 4.2 Поток данных виджета

```
запись транзакции  →  пересчёт снимка  →  DataStore(widget_state)  →  GlanceAppWidget.updateAll()
```

**Ключевое решение: виджет не читает Room напрямую и не считает балансы.**
Он читает готовый снимок:

```kotlin
@Serializable
data class WidgetSnapshot(
    val totalBalanceFormatted: String,     // "1 240 500 сум" — уже отформатировано
    val baseCurrencySymbol: String,
    val monthExpenseFormatted: String,
    val quickCategories: List<QuickCategory>,  // 4–6 самых частых: id, name, icon, color
    val rateStale: Boolean,                // курс старше N дней → показать пометку
    val computedAt: Long,
)
```

Почему так:
* Виджет живёт в **чужом процессе** (в процессе лаунчера рисуется, но обновляется из твоего процесса,
  который может быть убит). Открывать Room, ждать курсы и считать агрегаты в момент отрисовки — источник
  «Загрузка…», ANR-подобных задержек и пустых виджетов.
* Снимок обновляется в трёх случаях: (1) после любой записи в БД, (2) после синхронизации курсов,
  (3) по расписанию раз в сутки (смена месяца, устаревание курса).
* Форматирование чисел делается на стороне приложения, где есть настройки локали и `display_scale`,
  а не в композиции виджета. Это же снимает вопрос «как показывать деньги в виджете, не заводя Double» —
  в снимке лежит строка (I-1 соблюдён буквально).

### 4.3 Что происходит при добавлении траты из виджета

Честный ответ на «1–2 тапа»: **произвольную сумму в один тап ввести нельзя** — её надо чем-то набрать.
Реалистичные сценарии:

| Сценарий | Тапов | Как |
|---|---|---|
| Тап по категории → полупрозрачная Activity с цифровой клавиатурой → «✓» | 1 тап + ввод суммы + 1 тап | Основной сценарий |
| Тап по кнопке «+» → полный экран добавления в приложении | 1 тап + заполнение | Запасной |
| Тап по пресету («Кофе 15 000») → запись сразу, без экрана, с undo-снекбаром | **1 тап** | Для регулярных одинаковых трат |

Пресеты — единственный способ получить настоящий «один тап», и это неплохая идея именно для трекера
повседневных трат (обед, транспорт, кофе). **ВОПРОС 5:** нужны ли пресеты в первой версии виджета?

Технически: тап → `PendingIntent` (`actionStartActivity` для сценариев 1–2, `actionRunCallback` для пресета).
Для пресета обработчик обязан завершиться быстро: запись идёт через `goAsync()`/WorkManager,
иначе процесс может быть убит между тапом и коммитом в БД.

### 4.4 Ограничения платформы, о которые ты споткнёшься

1. **`updatePeriodMillis` — минимум 30 минут, и он не гарантируется.** На «обновление баланса» полагаться
   нельзя; единственный надёжный путь — push из приложения (`updateAll()`) после каждой записи.
2. **Процесс приложения может быть мёртв**, когда пользователь смотрит на виджет. Виджет обязан
   отрисовываться из снимка, без запуска приложения.
3. **Прямая загрузка (Direct Boot).** До первой разблокировки телефона зашифрованное хранилище недоступно,
   Room и обычный DataStore не открываются. Виджет должен уметь показать заглушку вместо краха.
4. **Android 12+: `PendingIntent` обязан быть `FLAG_IMMUTABLE`** (Glance это делает сам, но если полезешь
   в RemoteViews руками — поймаешь `IllegalArgumentException` на старте).
5. **Ограничения RemoteViews действуют и в Glance**: доступен ограниченный набор «виджетов»,
   нет произвольного рисования, нет анимаций, ограничение на размер транзакции RemoteViews
   (большой список в виджете → `TransactionTooLargeException`). Отсюда: не более 6 быстрых категорий.
6. **Размеры и `sizeMode`.** Пользователь растягивает виджет как хочет; нужно предусмотреть
   минимум два размера (компактный: только баланс; расширенный: баланс + категории).
7. **Тёмная тема, Material You, скругления Android 12+**: виджет должен читать системные цвета,
   иначе будет выглядеть чужеродно; в Glance это `GlanceTheme.colors`.
8. **Батарейные ограничения** (Doze, ограничения производителей — особенно Xiaomi/Huawei):
   фоновые обновления могут не выполняться часами. Ещё один аргумент за «снимок + push после записи».
9. **Отладка виджетов болезненна**: нет превью, которое отражает реальность; переустановка приложения
   иногда оставляет виджет в состоянии «Загрузка…» до перезагрузки лаунчера. Закладывай на виджет
   больше времени, чем кажется по объёму кода (см. этап 4 в §6.2).

## 5. Слои приложения

### 5.1 ADR-010: модульность

**Контекст.** Многомодульность в Ivy (30+ Gradle-модулей) — оправдана для команды, вредна для соло-разработки
через агента: агент тратит контекст на навигацию по `settings.gradle.kts` и на межмодульные зависимости.
Один модуль — быстрее в разработке, но теряется физическая граница «сюда Android не пролезает».

**Выбор: четыре модуля.**

```
:core:money      — чистый Kotlin (без Android SDK!). Money, CurrencyCode, FxRate,
                   convert(), правила округления, вычисление курсовой разницы.
                   Здесь живут ВСЕ инварианты I-1..I-13. 100% покрытие юнит-тестами.
:core:data       — Room (entity/dao/db, миграции), репозитории, DataStore-настройки,
                   провайдеры курсов (сеть), CSV-импорт, бэкап/восстановление.
:app             — Compose UI, ViewModel'и, навигация, DI-контейнер, форматирование.
:widget          — Glance-виджет и построитель снимка.
```

Зависимости строго в одну сторону: `:app` → `:core:data` → `:core:money`; `:widget` → `:core:data`.
`:core:money` не знает ни про Room, ни про Android — поэтому его тесты выполняются на JVM за миллисекунды,
без эмулятора и без Robolectric. Это прямо про твоё «минимум ручной отладки»: самая опасная логика
проверяется быстрее всего.

**Где живёт бизнес-логика.** В `:core:money` (арифметика, конверсия, инварианты) и в use-case-функциях
внутри `:core:data` (сборка отчёта, расчёт баланса, импорт). В ViewModel — только состояние экрана
и вызовы use-case'ов. В Composable — только отрисовка. Правило для промптов агенту:
*«если в Composable появилось арифметическое действие над деньгами — это ошибка ревью»*.

**Поток данных.** Однонаправленный: Room `Flow` → use-case (map в domain-модель) → ViewModel `StateFlow`
→ Compose. Запись — через suspend-функции репозитория. Никаких `LiveData`, никаких двусторонних биндингов.

### 5.2 Что покрывается тестами

| Уровень | Что тестируем | Чем |
|---|---|---|
| `:core:money` | Каждый инвариант I-1…I-13 отдельным тестом; округление; переполнение; кросс-курсы; курсовая разница | JUnit, чистый JVM |
| `:core:data` | Миграции (`MigrationTestHelper`); запросы отчётов на фиксированном наборе данных; парсер Monefy CSV на golden-файлах; идемпотентность импорта | Room in-memory, JUnit |
| ViewModel | Пара ключевых сценариев (добавление операции, смена периода) | Coroutines Test |
| UI | **Не тестируем автоматически.** Дорого, хрупко, для одного пользователя не окупается | — |
| Виджет | Тестируем только построитель снимка (чистая функция); саму отрисовку — руками | JUnit |

Такое распределение сознательно смещает всю проверяемость в чистый Kotlin: агент пишет тест и код
одним промптом, тесты идут секунды, и ты видишь красное/зелёное вместо ручной отладки на устройстве.

### 5.3 Библиотеки: минимально достаточный набор

| Библиотека | Зачем | Что сломается без неё |
|---|---|---|
| **Kotlin Coroutines + Flow** | Асинхронность и реактивность БД | Придётся писать колбэки/`LiveData`; Room всё равно предлагает `Flow` |
| **Jetpack Compose + Material3** | UI | Альтернатива — XML-вёрстка: ещё один язык для агента, вдвое больше файлов на экран |
| **Room** | SQLite: маппинг, DAO, миграции, `Flow`-запросы, тесты миграций | Ручной `SQLiteOpenHelper` + курсоры: сотни строк шаблонного кода, где агент ошибается чаще всего, и никакого `MigrationTestHelper` |
| **kotlinx-serialization** | JSON: бэкап, ответы провайдера курсов, снимок виджета | Ручной парсинг JSON — источник тихих ошибок |
| **DataStore (Preferences)** | Настройки + снимок виджета | `SharedPreferences` (синхронный I/O, нет `Flow`) |
| **WorkManager** | Ежедневная синхронизация курсов, автобэкап | Нет надёжного планировщика; `AlarmManager` + Doze — самостоятельная головная боль |
| **OkHttp** | Один GET в день | Можно на `HttpURLConnection`, но retry/timeout/TLS придётся писать руками |
| **kotlin-csv** (`doyaaaaaken/kotlin-csv`) | Разбор экспорта Monefy | Самописный парсер CSV сломается на кавычках, запятых внутри поля, BOM, `\r\n` — классические грабли, дающие «почти работает» |
| **Glance** | Виджет | RemoteViews + XML (см. ADR-009) |
| **Detekt** (dev) | Автоматическая проверка части инвариантов (запрет `Double` в money-пакетах, запрет `fallbackToDestructiveMigration`) | Инварианты придётся проверять глазами на каждом ревью агентского кода |

**Чего сознательно нет:**

* **Hilt/Dagger.** Для 4 модулей и ~15 зависимостей ручной контейнер (`class AppContainer`, ~60 строк)
  делает то же самое. Цена Hilt — KSP-кодогенерация, чьи ошибки выглядят как «cannot find symbol
  в сгенерированном файле», а это худший вид обратной связи для агента: причина ошибки не в том файле,
  который агент видит. *ADR-011: выбираем ручной DI. Пересмотреть, если модулей станет >8.*
* **Retrofit.** Один HTTP-запрос в сутки не окупает интерфейсы, конвертеры и рефлексию.
* **Библиотеки графиков** (Vico/MPAndroidChart). На первых этапах — два простых графика на Compose `Canvas`.
  Все они работают с `Float` — это граница, за которой деньги превращаются в неточные числа;
  чем позже мы её проведём, тем лучше. Вводить, когда графики реально понадобятся.
* **Arrow** (как в Ivy). `Either`/`Option` — красиво, но это ещё один слой абстракций,
  который агент должен держать в голове. Обычные `sealed class Result` и исключения понятнее.
* **Paging 3.** Понадобится, если список транзакций начнёт тормозить. На 50k строк с Room + `Flow`
  и `LazyColumn` — не понадобится.

### 6.2 Этапы

Оценки — **часы твоего времени**: постановка задачи агенту, ревью, отладка, приёмка.
Не время работы агента.

**Этап 0. Фундамент (6–10 ч).**
`:core:money` целиком с тестами на все инварианты; схема БД v1 + Room + тест миграции-заглушки;
пустое приложение, которое запускается. Ничего пользовательского. Это самый важный этап:
всё, что построено на неверной модели денег, придётся переделывать.
*Критерий готовности:* тесты на I-1…I-13 зелёные, `:core:money` не зависит от Android.

**Этап 1. Ручной учёт в одной валюте (12–18 ч).**
Счета, категории, добавление/редактирование/удаление расхода и дохода, список операций с
группировкой по дням, баланс счёта. Экспорт/импорт JSON-бэкапа (сразу, до накопления данных!).
*Критерий:* можно вести учёт руками. **Здесь приложение уже полезно.**

**Этап 2. Мультивалютность (10–16 ч).**
Таблица курсов, провайдер + WorkManager, ручной ввод курса, снимки в транзакциях,
сводный баланс в базовой валюте, отчёт за период по категориям (исторические курсы),
строка «переоценка FX», состояние `RateMissing` в UI.
*Критерий:* сводные цифры сходятся с ручной проверкой на калькуляторе для смешанного набора валют.

**Этап 3. Импорт из Monefy (8–14 ч).**
Парсер по спецификации `docs/MONEFY_IMPORT.md` + dry-run + `NEEDS_REVIEW` + алиасы +
идемпотентность + откат батча + курсы из CSV.
*Критерий:* годовые контрольные суммы (§6 спецификации) сходятся до копейки,
6 943 строки дают 6 932 операции + 4 перевода + 3 начальных остатка,
две аномальные строки предъявлены пользователю, а не проглочены.

**Этап 4. Переводы и курсовая разница (6–10 ч).**
Одна строка с двумя суммами, UI перевода с подстановкой рыночного курса и возможностью
переопределить фактический, отчёт «потери на конвертациях», исключение переводов из потоков.
*Критерий:* перевод между UZS и RUB не появляется ни в доходах, ни в расходах, а разница видна отдельно.
**После этого этапа Monefy можно удалять.**

**Этап 5. Виджет (8–15 ч).**
Снимок, Glance-виджет с балансом и расходами месяца, быстрые категории, полупрозрачный экран ввода суммы,
(опционально) пресеты.
*Критерий:* трата добавляется с домашнего экрана и виджет обновляется сразу.

**Этап 6. Полировка (10–20 ч, ограничить по времени сознательно).**
Автобэкап по расписанию с ротацией, графики, поиск/фильтры, темы, иконки категорий,
удобство ввода (калькулятор в поле суммы), Material You.

**Итого: 50–83 ч по этапам + 20–30% на непредвиденное = 70–115 ч.**

Порядок выбран так, что каждый следующий этап добавляется **поверх работающего приложения**
и не требует переделки предыдущего: модель денег (0) → ручной ввод (1) → курсы (2) → массовые
данные (3) → сложные операции (4) → удобство (5, 6). Единственная жёсткая зависимость —
этап 0 перед всем остальным.

## 8. Где я считаю твои требования ошибочными или неточными

1. **«Виджет: быстрое добавление траты в 1–2 тапа».** Для произвольной суммы это невозможно:
   сумму нужно ввести. Честная формулировка — «1 тап до экрана ввода суммы» или «1 тап для
   заранее заданного пресета». Если ждать буквально 1–2 тапа для любой траты, виджет будет
   ощущаться как невыполненное обещание. См. §4.3.
2. **«Полностью офлайн; курсы подтягиваются при наличии сети».** Это не «полностью офлайн»,
   а «офлайн-first с опциональной сетью». Разница существенна: приложению нужно разрешение
   `INTERNET`, а значит и явная политика на случай «курса нет» (§2.5). Формулировка «полностью офлайн»
   опасна тем, что провоцирует спроектировать систему, которая молча подставляет неверный курс,
   лишь бы не показывать ошибку.
3. **«Фиксация курсовой разницы»** — если под этим понимается хранение разницы отдельным числом,
   то это ошибка (второй источник истины, §2.4). Фиксируется не разница, а **два снимка курсов
   и обе суммы**; разница из них выводится однозначно и всегда согласована.
4. **Требования не включают самого важного для замены Monefy: критерия «сошлось».**
   Предлагаю добавить явное приёмочное требование: после импорта итоги по месяцам должны совпасть
   с Monefy с точностью до объяснимых округлений. Без этого критерия ты не сможешь доверять
   новому приложению, а значит, не перейдёшь на него.
5. **Про «вне скоупа».** Согласен со всем списком и в архитектуре ничего под синхронизацию
   не закладываю (нет `is_deleted`, нет ревизий, нет `device_id`). Единственное решение,
   которое **выглядит** как задел на будущее, — UUID вместо autoincrement (ADR-007), но оно
   обосновано сегодняшними задачами бэкапа и импорта, а не гипотетическим облаком. Если этот
   аргумент тебя не убеждает — скажи, поменяю на `INTEGER AUTOINCREMENT`, цена перехода на этапе 0
   близка к нулю.
6. **Пункт про «может, просто взять готовое» снят.** Проверка на практике показала, что импорт CSV
   и автозагрузка курсов в My Expenses платные (§1.4, §1.9), то есть готовое решение не закрывает
   требования №4 и №6 без покупки лицензии и всё равно оставляет тебя без контроля над кодом.
   Решение писать своё — обосновано.
