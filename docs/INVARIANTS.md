# Инварианты Corriente

Чек-лист для проверки любого кода (в том числе сгенерированного агентом).
Нарушение любого пункта — баг, даже если тесты зелёные.
Полное обоснование — в `docs/ARCHITECTURE.md`, §2. Номера стабильны, снятые не переиспользуются.

В приложении **нет конвертации валют и нет сетевого кода** (ADR-012, ADR-013).

**Деньги**
* **I-1.** Деньги нигде не представлены `Double`/`Float`: ни в БД, ни в domain, ни в DTO, ни в UI-state,
  ни в снимке для виджета. `BigDecimal` допустим только как транзитный тип внутри парсинга.
* **I-2.** Арифметика над `Money` допустима только при совпадении валют; несовпадение = исключение,
  а не приведение.
* **I-3.** Сложение/вычитание/отрицание — через `Math.addExact/subtractExact/negateExact`
  (умножение на целое — `Math.multiplyExact`). Переполнение приводит к падению, а не к неверному
  числу. Запрет распространяется и на арифметику над `Minor.raw` / `amountMinor` **вне** `Money`:
  накапливать суммы обязан `Money.plus`/`minus`, а не `Long::plus` над сырыми минорными единицами
  (статический скан `InvariantGuards` ловит ссылку на `Long::plus/minus/times` рядом с суммами).
* **I-4.** Округление до минорных единиц происходит ровно один раз и только там, где деление
  действительно нужно (вывод курса сделки, деление суммы). Промежуточные вычисления не округляются.

**Валюты**
* **I-7а.** Для перевода между разными валютами источник истины — **две суммы**. Курс сделки
  всегда выводится из них и нигде не хранится отдельно.
* **I-8.** Отчёты и балансы **не конвертируются никогда**: каждая цифра принадлежит одной валюте
  и подписана ею. Сложение сумм в разных валютах невозможно на уровне типов (см. I-2).
* **I-9.** Никакая производная величина (баланс, итог за период) не хранится как единственный
  источник истины. Если она материализована — это кэш, пересчитываемый в той же транзакции БД.
* **I-11.** Транзакции с `kind = TRANSFER` не входят ни в доходы, ни в расходы, ни в отчёты по категориям.
* **I-12.** Курсовая разница и фактический курс обмена вычисляются из двух сумм перевода,
  не вводятся пользователем и не хранятся как независимые значения.
* **I-14.** Валюта — строка в таблице `currency`, а не enum в коде. Список валют **не ограничен**:
  справочник засеивается полным перечнем ISO-4217, пользователь помечает нужные как активные.
  Добавление валюты — INSERT или смена флага, без миграции и без релиза.
* **I-15.** Валюта транзакции всегда равна валюте счёта. Покупка в чужой валюте с карты
  записывается в валюте карты (как её видит банк); реальный обмен моделируется переводом.
* **I-23.** **Валюта счёта неизменна** после первой операции по нему. Сменить валюту нельзя —
  только создать новый счёт и перевести остаток. Это не педантизм: ровно из-за нарушения
  этого правила в экспорте Monefy появились строки, где 66 667 USD равны 66 667 RUB
  (`docs/MONEFY_IMPORT.md`, §4).

**Изоляция и данные**
* **I-24.** В приложении нет сетевого кода и нет разрешения `INTERNET` (ADR-013). Любая задача,
  решение которой требует сходить в сеть, решается иначе или не решается.
* **I-19.** Импорт идемпотентен: повторный импорт того же файла не создаёт дублей; каждый импорт —
  это `import_batch`, удаляемый целиком одной операцией.
* **I-20.** Никакого `fallbackToDestructiveMigration()`. Каждая миграция — явный `Migration`-объект
  с тестом. Перед применением миграции автоматически создаётся копия файла БД.
* **I-21.** Бэкап содержит версию схемы и восстанавливает состояние полностью, включая справочники.
  Восстановление из бэкапа более старой версии проходит через ту же цепочку миграций.
* **I-22.** Удаление данных — физическое. Флагов `isDeleted` нет (они нужны только для синхронизации,
  которой нет; см. Ivy как пример того, во что это вырождается).
* **I-25.** Разбор чисел при импорте — только явный: запятая = разделитель тысяч, точка = десятичный
  (`docs/MONEFY_IMPORT.md`, §2). Локале-зависимый парсинг денег запрещён везде, включая ввод
  с клавиатуры: `NumberFormat.getInstance()` в денежном пути — ошибка ревью.

**Снятые инварианты** (номера не переиспользовать):
I-5, I-6, I-7, I-8а, I-13, I-16, I-17, I-18 — все касались хранения курсов, историчности
и поведения при отсутствии курса. Сняты решением ADR-013: курсов в приложении нет.
I-10 поглощён I-7а и структурой таблицы (перевод физически не может существовать «половинкой»).
