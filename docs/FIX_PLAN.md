## 0. Правила работы (обязательны для исполнителя)

Действуют **все** правила `BUILD_PLAN.md` §0 без изъятий. Дополнительно к ним:

1. **Одна задача `Fx.y` = один коммит**, сообщение начинается с ID: `F0.1: ограничение длины ввода суммы`.
2. **Каждая задача начинается с теста, который падает.** Сначала пишется тест, воспроизводящий
   дефект, убеждаемся что он красный, потом чинится код. Задача без такого теста не считается
   сделанной — половина дефектов ниже существует именно потому, что путь не покрыт.
3. **Перед коммитом:** `./gradlew check` зелёный. Для задач, помеченных `[БД]`, дополнительно
   `./gradlew connectedCheck` на запущенном эмуляторе `corriente`.
4. **Порядок задач соблюдать.** Он не произволен: F0.2 вводит механизм, на который опираются
   F0.3–F0.6 и половина P1. Внутри одного приоритета порядок можно менять, между приоритетами — нет.
5. **Не расширять скоуп.** Замеченное сверх задачи — в `docs/BACKLOG.md` (сейчас он пуст),
   а если это тянет на направление развития — предложить пункт в `ROADMAP.md` отдельным коммитом.
6. **Схема БД.** Миграции `v1 → v2` и далее **разрешены** (решение от 2026-09-02, отменяет запрет
   `BUILD_PLAN.md` §8). Каждая миграция — явный `Migration`-объект + тест через `MigrationTestHelper`,
   `fallbackToDestructiveMigration` запрещён навсегда (I-20). В этом документе схему трогает
   только F1.5; всё остальное чинится без миграции.
7. **Инварианты не обходить.** Если исправление требует нарушить инвариант — остановиться и
   спросить: либо инвариант неверен и меняется осознанно, либо задача поставлена неправильно
   (`BUILD_PLAN.md` §0 правило 5).
8. **Ручная проверка на эмуляторе** для задач с пометкой `[ручная]` — сценарий описан в §7.
   `adb shell input text` не умеет кириллицу, вводить латиницей.

### Формат задачи

Каждая задача ниже описана блоком: **Симптом** (что видит пользователь) → **Причина**
(точное место в коде) → **Что сделать** → **Критерий приёмки** → **Тесты**. Исполнителю
не нужно самостоятельно искать причину — она уже локализована; нужно проверить, что она
не изменилась с момента написания документа, и чинить.

## 2. Приоритет P0 — падения и тихая порча данных

### F0.1 — Переполнение при вводе суммы роняет экран

**Симптом.** Открыть ввод расхода, нажать «9» девятнадцать раз — приложение падает
(`NumberFormatException`). То же на поле «начальный остаток» счёта и на суммах перевода, если
вставить длинное число.

**Причина.** `core/money/src/main/kotlin/com/corriente/money/AmountInput.kt:21-30` —
`appendDigit` не ограничивает длину целой части. `AmountInput.kt:56-62` — `toMinorOrNull`
делает `.toLong()` на склеенной строке цифр и бросает, а не возвращает `null`. Исключение
вылетает не при нажатии, а при отрисовке: `TxnEntryUiState.canSave`
(`app/.../txnentry/TxnEntryViewModel.kt:79-83`) читается в композиции
(`TxnEntryScreen.kt:174`), то есть падает кадр, а не обработчик.

**Что сделать.**
1. В `AmountInput` ввести `private const val MAX_TOTAL_DIGITS = 18` (`Long.MAX_VALUE` — 19 знаков,
   один оставляем на перенос при сложении калькулятора). `appendDigit` возвращает `this` без
   изменений, если `integerDigits.length + currency.minorUnits >= MAX_TOTAL_DIGITS`.
2. `toMinorOrNull` заменить `.toLong()` на `.toLongOrNull() ?: return null` — «пояс и подтяжки»
   на случай, если ограничение обойдут через `fromText`.
3. `fromText` ограничение получает автоматически, потому что идёт через `appendDigit`.
4. Проверить, что `AmountInput.fromMinor` симметричен: `fromMinor(toMinorOrNull(x))` == `x`
   для граничных значений.

**Критерий приёмки.** Двадцать пять нажатий «9» на клавиатуре не меняют экран после 18-го
и не роняют приложение; поле «начальный остаток» с 30 цифрами сохраняется как обрезанное
значение, а не падает.

**Тесты.** `core/money/src/test/.../AmountInputTest.kt`: цифра сверх лимита игнорируется;
`toMinorOrNull` на предельном значении даёт `Long`, на заведомо превышающем — `null`;
round-trip `fromMinor`/`toMinorOrNull` на `Long.MAX_VALUE / 100`.

**`[ручная]`** — сценарий 1 из §7.

### F0.2 — Ни один путь записи не обрабатывает ошибок

**Симптом.** Любая ошибка репозитория роняет приложение без сообщения. Достоверно
воспроизводимые случаи:
* создать две категории с одинаковым именем и типом → уникальный индекс `ux_category_name_kind`
  → `SQLiteConstraintException`;
* открыть редактор счёта без операций, в другом окне добавить по нему операцию, сохранить
  счёт → `check(!hasTransactions)` в `AccountRepository.setCurrencyAndOpeningBalanceBeforeFirstUse`;
* сохранить операцию, у которой валюта суммы разошлась с валютой счёта (после F0.3 такой путь
  останется достижимым при гонке архивирования) → `require` в `TxnRepository`.

**Причина.** Все записи выглядят так:
`viewModelScope.launch { repo.doSomething() }` — без `try`. См.
`TxnEntryViewModel.kt:242-252`, `TransferEntryViewModel.kt:188-197`,
`AccountsViewModel.kt:171-191, 195-205`, `CategoriesViewModel.kt:106-116, 119-129, 145-151`,
`CurrenciesViewModel.kt:58-69`, `WidgetSettingsViewModel`. Необработанное исключение в
`viewModelScope` доходит до обработчика по умолчанию и убивает процесс. Единственные два места
в `:app`, где ошибки ловятся, — `BackupViewModel` и `ImportViewModel`.

**Что сделать.**
1. Завести `app/src/main/kotlin/com/corriente/app/ui/common/UiMessage.kt`: `data class UiMessage(val text: String)`
   плюс маленький хелпер, который ViewModel подмешивает себе:
   ```kotlin
   protected val _messages = MutableStateFlow<UiMessage?>(null)
   val messages: StateFlow<UiMessage?> = _messages
   fun consumeMessage() { _messages.value = null }
   protected fun ViewModel.launchWrite(onError: (Throwable) -> String, block: suspend () -> Unit)
   ```
   Никаких «умных» абстракций (`BUILD_PLAN.md` §0 правило 4): один базовый класс
   `WritingViewModel : ViewModel()` с тремя членами, без generic-обвязки.
2. Перевести на него **все** записи в перечисленных ViewModel. Текст ошибки — человеческий
   и по делу («Категория «Еда» уже есть»), а не `e.message`.
3. Каждый экран показывает сообщение через `Snackbar` в своём `Scaffold`
   (`SnackbarHost` + `LaunchedEffect(message)`), после показа зовёт `consumeMessage()`.
4. Отдельно: `AccountsViewModel.save` перед `setCurrencyAndOpeningBalanceBeforeFirstUse`
   перечитывает `accounts.hasTransactions(id)` и, если операции появились, сохраняет только
   имя и флаги, а пользователю показывает «валюта уже зафиксирована первой операцией».

**Критерий приёмки.** Ни один сценарий из «Симптом» не роняет приложение; в каждом появляется
снекбар с внятным текстом; данные остаются в согласованном состоянии.

**Тесты.** Юнит-тесты ViewModel с фейковыми DAO, которые бросают на нужной операции: проверяем,
что `messages` заполнился, состояние формы не потерялось, `finished` остался `false`.

### F0.3 — Правка операции на архивном счёте переносит её на чужой счёт

**Симптом.** Счёт заархивирован (единственный способ убрать счёт с операциями). Открыть старую
операцию по нему, поправить заметку, сохранить — операция уезжает на первый активный счёт.
Если у того другая валюта, приложение вместо этого падает (см. F0.2).

**Причина.** `app/.../txnentry/TxnEntryViewModel.kt:164-165`:
```kotlin
val selectedAccountId = f.selectedAccountId?.takeIf { id -> options.any { it.id == id } }
    ?: options.firstOrNull()?.id
```
`options` строятся из `accounts.observeActive()` (строка 151) — архивного счёта там нет,
`takeIf` даёт `null`, срабатывает подстановка первого активного. `save()` (строка 239) берёт
уже подменённый `selectedAccountId`. Идентичный дефект в
`TransferEntryViewModel.kt:127-131` — и там он вдвойне неприятен, потому что подменить может
обе стороны перевода.

**Что сделать.**
1. В обеих ViewModel список счетов для формы строить как «активные **плюс** счета, на которые
   ссылается редактируемая операция». Взять `accounts.observeAll()`, из него собрать `options`
   активных, и добавить архивные только если их id встречается в `editingTxnId`-операции.
   Архивный вариант помечать в `AccountOption`/`TransferAccount` флагом `isArchived` и
   показывать на чипе (например «Карта (архив)»).
2. Подстановку «первый активный» оставить **только** при создании (`editingTxnId == null`).
   При редактировании, если счёт операции не нашёлся вообще (удалён), — не подставлять ничего,
   заблокировать сохранение и показать сообщение.

**Критерий приёмки.** Правка заметки у операции на архивном счёте сохраняет её на том же счёте;
чип этого счёта виден и выбран; сумма и валюта не меняются.

**Тесты.** `TxnEntryViewModelTest`: фейк с одним активным и одним архивным счётом, редактируем
операцию архивного — `uiState.selectedAccountId` равен архивному, `save()` вызывает
`updateEntry` с ним же. Аналогичный тест в `TransferEntryViewModelTest` на обе стороны перевода.

### F0.4 — Правка операции с архивной категорией стирает категорию

**Симптом.** Категория заархивирована. Открыть старую операцию с ней, поправить сумму,
сохранить — категория обнуляется, операция становится «без категории» и выпадает из отчётов.

**Причина.** `TxnEntryViewModel.kt:175`:
```kotlin
selectedCategoryId = f.selectedCategoryId?.takeIf { id -> kindCategories.any { it.id == id } }
```
`kindCategories` фильтруются из `categories.observeActive()` (строка 153). Архивной там нет →
`null` → `save()` (строка 244) пишет `categoryId = null`.

**Что сделать.** Ровно та же схема, что в F0.3: список категорий формы = активные того же вида
**плюс** категория редактируемой операции, даже архивная, с пометкой «(архив)» на чипе.
Обнуление категории должно быть только явным действием пользователя (чип «Без категории»).

**Критерий приёмки.** Правка суммы у операции с архивной категорией сохраняет категорию.
Отчёт по категориям за прошлый период после такой правки не меняется.

**Тесты.** `TxnEntryViewModelTest`: редактирование операции с архивной категорией — категория
остаётся в `uiState.categories`, выбрана, и уходит в `updateEntry` неизменной.

### F0.5 — Импорт пишет операции в счёт чужой валюты

**Симптом.** В приложении уже есть счёт «Наличные» в RUB. В экспорте Monefy счёт с тем же именем
ведётся в USD. Импорт молча кладёт USD-операции в RUB-счёт: баланс счёта считается сложением
разных валют, `MoneyFormatter` подставляет чужие минорные единицы, данные испорчены необратимо.

**Причина.** `core/data/.../imports/MonefyImportRepository.kt:56-69`: существующий счёт
переиспользуется **по имени**, валюта не сверяется:
```kotlin
val existingAccounts = db.accountDao().observeAll().first().associateBy { it.name }
...
accountIdByName[planned.name] = existing?.id ?: run { /* создать */ }
```
Проверок I-15 («валюта операции равна валюте счёта») здесь нет, потому что запись идёт через
`db.txnDao().insert(...)` напрямую, минуя `TxnRepository` (см. F1.2).

**Что сделать.**
1. Переиспользовать существующий счёт только при совпадении **имени и валюты**.
2. При совпадении имени и расхождении валюты — не импортировать молча. Добавить в
   `MonefyImportPlanner` новую причину `ReviewReason.EXISTING_ACCOUNT_CURRENCY_MISMATCH` и
   решения `ReviewDecision`: «создать отдельный счёт `<имя> (USD)`» либо «прервать импорт».
   Планировщик не знает про БД, поэтому проверку делает `MonefyImportRepository` до начала
   транзакции и возвращает её как отказ, который `ImportViewModel` показывает карточкой —
   ровно тем же механизмом, что уже работает для `NEEDS_REVIEW` (`applyReviewDecisions`).
   Проще и допустимо: сделать эту проверку на шаге dry-run, дав `MonefyImportPlanner.plan`
   опциональный параметр `existingAccounts: List<Pair<String, CurrencyCode>> = emptyList()`.
3. Пока решение не принято, кнопка «Импортировать» заблокирована.

**Критерий приёмки.** Импорт файла со счётом-тёзкой в другой валюте не пишет ни одной строки,
пока пользователь не выбрал вариант; выбранный вариант «отдельный счёт» создаёт новый счёт
и все операции попадают в него.

**Тесты.** `[БД]` `MonefyImportRepositoryInstrumentedTest`: в БД счёт `Cash/RUB`, план с
`Cash/USD` → импорт отклонён, `txn` пуст. После решения «отдельный счёт» — два счёта,
у каждой операции валюта совпадает с валютой её счёта. Плюс юнит-тест планировщика на новую
причину.

### F0.6 — Быстрый ввод из виджета может потерять операцию

**Симптом.** Тап по категории в виджете → сумма → «Сохранить». Если в этот момент система
пересоздаёт Activity (поворот, смена темы, нехватка памяти), операция не записывается,
а пользователь видит закрытое окно и считает, что записал.

**Причина.** `app/.../quick/QuickExpenseActivity.kt:107-112` — запись идёт в
`rememberCoroutineScope()`, то есть в скоупе композиции: он отменяется вместе с ней, и
`addExpense` может не доехать до конца. Та же схема в
`ChangeActiveAccountActivity.kt:69-72`. Дополнительно оба места не ловят исключений (см. F0.2)
и не показывают, что запись идёт.

**Что сделать.**
1. Заменить `rememberCoroutineScope()` на `lifecycleScope` Activity (у `ComponentActivity` он
   есть без новых зависимостей): запись переживает пересоздание композиции.
2. Обернуть запись в `runCatching`; при ошибке — не закрывать окно, показать текст и
   разблокировать кнопку.
3. `finish()` вызывать только после успеха.
4. Заодно: `saving = true` уже есть, но ничем не отображается — добавить индикатор в кнопке.

## 3. Приоритет P1 — инварианты, бэкап, импорт

### F1.1 — Итоги дня складываются мимо `Math.addExact`

**Симптом.** Дефекта в поведении сегодня нет, но нарушен I-3: переполнение даст неверное число
вместо падения. Статический скан `verifyInvariantGuards` этот случай не ловит.

**Причина.** `app/.../transactions/TransactionsViewModel.kt:160-173` — `dayTotals` работает на
голых `Long` через `nets.merge(code, -txn.amount.amount.raw, Long::plus)`; унарный минус и
сложение идут в обход `Money`, а значит и в обход `Math.addExact`/`negateExact`.

**Что сделать.** Переписать `dayTotals` на `Map<CurrencyCode, Money>`: накапливать
`Money.plus`/`Money.minus`, которые уже используют `*Exact` (I-3), и только на выходе
форматировать. Проверить, нет ли такой же арифметики в других местах
(`ReportViewModel.withShares:81` — это доли, там `Long` уместен, но переполнение при
`total * 100` возможно: заменить на `Math.multiplyExact` или считать через `BigDecimal`,
как транзитный тип, что разрешено I-1).

**Критерий приёмки.** `verifyInvariantGuards` расширен правилом «в `:app` и `:core:data` нет
арифметики над `amountMinor`/`amount.raw` вне `Money`» **либо** (если правило даёт ложные
срабатывания) в `InvariantGuards` добавлено более узкое: запрет `Long::plus` и `Long::minus`
как ссылок на функции в файлах, где встречается `Minor`. Правило покрыто `InvariantGuardsTest`.

**Тесты.** `TransactionsViewModelTest`: итог дня из расхода и дохода одной валюты; итог дня
из двух валют — две строки; переполнение (`Long.MAX_VALUE` в двух операциях) бросает,
а не даёт отрицательное число.

### F1.2 — Импорт пишет `TxnEntity` мимо проверок `TxnRepository`

**Симптом.** Класс дефектов, из которого F0.5 — только первый обнаруженный случай. Любая
будущая правка правил записи операции (I-1, I-11, I-15) не подействует на импорт, потому что
импорт не проходит через единственное место, где эти правила enforced.

**Причина.** `MonefyImportRepository.import` (строки 97-135) собирает `TxnEntity` руками и
зовёт `db.txnDao().insert(...)`. `TxnRepository` с его `requireAmountMatchesAccount` не
участвует. Комментарий в `TxnEntity.kt:20-27` прямо говорит, что эти правила обязан проверять
репозиторий — импорт этот контракт нарушает.

**Что сделать.** Не тащить импорт через `TxnRepository` целиком (там `UUID` и `System.currentTimeMillis`
на каждую операцию, батчу это не подходит), а вынести проверки в чистую функцию
`:core:data`, которую вызывают оба пути:
```kotlin
// core/data/.../repository/TxnInvariants.kt
fun requireValidTxn(entity: TxnEntity, accountCurrency: (String) -> String?)
```
проверяющую: сумма > 0; валюта совпадает с валютой счёта (I-15); у `TRANSFER` заполнены обе
стороны и `categoryId == null` (I-11); у `EXPENSE`/`INCOME` вторая сторона пуста. Подключить её
в `TxnRepository` и в `MonefyImportRepository` (вызов на каждую строку внутри транзакции, отказ
откатывает весь батч — это уже так работает).

**Критерий приёмки.** Попытка импорта, нарушающего I-11 или I-15, откатывает батч целиком и
даёт понятную ошибку; `txn` остаётся пустым.

**Тесты.** Юнит-тесты `requireValidTxn` на каждое правило. `[БД]` инструментальный тест:
план с заведомо битой строкой — после `import` в БД ноль операций и ноль батчей.

### F1.3 — Автобэкап: расписание пересобирается при каждом старте, статуса нет

**Симптом.** Пользователь включил автобэкап и не может убедиться, что он хоть раз отработал:
на экране нет ни даты последнего бэкапа, ни результата ручного запуска. Есть подозрение, что
при частом открытии приложения бэкап вообще не наступает.

**Причина.**
* `CorrienteApplication.kt:26-28` подписывается на `autoBackupSettings.config` и на **каждую**
  эмиссию зовёт `AutoBackupScheduler.apply`. `distinctUntilChanged` нет, а Room-инвалидация
  таблицы `app_setting` заставляет флоу переизлучать.
* `AutoBackupScheduler.kt:24-31` каждый раз строит `PeriodicWorkRequest` с
  `.setInitialDelay(1, TimeUnit.HOURS)` и ставит его с `ExistingPeriodicWorkPolicy.UPDATE`.
  Начальная задержка в периодическом запросе при повторной постановке — ровно тот механизм,
  который может отодвигать первый запуск бесконечно.
* `AutoBackupWorker` нигде не записывает результат; `AutoBackupScreen` показывает только папку
  и переключатель. Настройка `retention` читается (`AutoBackupSettings`), но менять её негде.

**Что сделать.**
1. `CorrienteApplication`: добавить `.distinctUntilChanged()` перед `onEach`.
2. `AutoBackupScheduler.apply`: убрать `setInitialDelay` из периодического запроса. Первый
   бэкап после включения запускать отдельным `OneTimeWorkRequest` (это уже умеет `runNow`).
3. `AutoBackupWorker`: после каждого запуска писать в `app_setting` ключи
   `auto_backup.last_run_at` (эпоха, мс) и `auto_backup.last_result` (`ok` / текст ошибки).
   Ключи — в `AutoBackupSettings` рядом с существующими, миграция не нужна.
4. `AutoBackupScreen`: показать «Последний бэкап: <дата>» либо «ещё не выполнялся», текст
   последней ошибки, и добавить выбор `retention` (3 / 7 / 14 / 30 файлов).
5. Добавить воркеру `Constraints`: `setRequiresStorageNotLow(true)` — записывать бэкап на
   переполненный диск бессмысленно.

**Критерий приёмки.** Проверка описана в сценарии 3 §7: включить автобэкап, дождаться/форсировать
запуск через `adb shell cmd jobscheduler run -f com.corriente.app <id>`, увидеть новый файл в
папке и обновлённую дату на экране; после отзыва доступа к папке — переключатель гаснет и виден
текст ошибки.

**Тесты.** Юнит-тесты `AutoBackupSettings` на новые ключи. `namesToPrune` уже покрыт
(`BackupRotationTest`) — дописать случай смены `retention` на меньшее значение.

### F1.4 — Восстановление из бэкапа: одна ошибка на всё, целостность не проверяется

**Симптом.** Любая проблема с файлом — битый JSON, обрезанная запись, ссылка на несуществующий
счёт — даёт одно и то же «Не удалось прочитать файл бэкапа». Понять, что не так, невозможно.
Отдельно: восстановление замещает данные необратимо, а копии «до восстановления» не делается,
хотя механизм `PreMigrationBackup` для такого уже есть.

**Причина.** `BackupViewModel.kt:48-55` схлопывает все исключения кроме
`BackupVersionException` в `BackupResult.Failed`. `BackupRepository.restore` (строки 57-83) не
валидирует полезную нагрузку до удаления текущих данных — целостность проверяют только внешние
ключи SQLite, уже внутри транзакции.

**Что сделать.**
1. В `BackupRepository` добавить чистую функцию `validate(payload: BackupPayload): List<String>`,
   которая до записи проверяет: все `currencyCode` есть в `currencies`; все `accountId`/
   `toAccountId`/`categoryId`/`importBatchId` операций разрешаются; суммы неотрицательны;
   у `TRANSFER` заполнены обе стороны, у остальных — нет; даты разбираются `LocalDate.parse`.
   Функция чистая — тестируется без БД.
2. `restore` вызывает `validate` первым делом; непустой список = отказ до всякого удаления.
3. Перед фактическим замещением делать копию текущей БД тем же механизмом, что
   `PreMigrationBackup` (вынести из него метод `copyDatabaseFile(context, dbName, reason)`),
   чтобы неудачное восстановление можно было отыграть назад.
4. `BackupResult` расширить вариантом `Invalid(val problems: List<String>)`; экран показывает
   первые три проблемы и число остальных.

**Критерий приёмки.** Восстановление из файла, где у операции указан несуществующий счёт,
не трогает текущие данные и объясняет причину. Успешное восстановление оставляет копию
предыдущей БД в `pre-migration/`.

**Тесты.** `BackupRoundTripTest` дополнить: валидный payload → пустой список проблем; payload
с висячей ссылкой → конкретная проблема; `[БД]` `BackupRepositoryInstrumentedTest`: после
отказа в БД остались прежние данные.

### F1.5 — Откат импорта реализован, но недоступен пользователю `[БД]`

**Симптом.** Импорт из Monefy — необратимая операция с точки зрения пользователя. Если

отчёт о том, что было импортировано, нигде не сохраняется.

**Что сделать.**
1. `ImportViewModel.confirm` передаёт в `import(...)` сериализованный `ImportSummary`

2. Новый экран «История импортов» (маршрут `import_history`, из «Настроек» рядом с «Импорт из
   Monefy»): список `import_batch` — файл, дата, число строк, сводка из `report_json`, кнопка
   «Откатить» с подтверждением.
3. `rollback` сузить: удалять только IMPORT-категории, которые остались без операций **и**

   коммитятся.
4. Так как это первая реальная миграция — проверить, что `PreMigrationBackup` действительно
   создаёт копию файла БД (до сих пор он был no-op, так как схема не менялась).

**Критерий приёмки.** Импорт → откат возвращает БД ровно в состояние до импорта: операции,
батч и созданные им категории удалены, категории прошлых импортов не тронуты.
`PreMigrationBackup` оставил копию `corriente.db.v1.<штамп>`.

**Тесты.** `[БД]` `AppDatabaseMigrationTest` — тест миграции 1→2.

## 4. Приоритет P2 — производительность и незавершённый UX

### F2.1 — Вся таблица операций в памяти, балансы за O(счета × операции)

**Симптом.** После импорта реальной истории из Monefy (годы данных) приложение заметно
подтормаживает на каждой записи; экран операций и отчёт лагают при вводе в поиск.

**Причина.** Узкое место архитектурное, а не точечное:
* `TxnDao.observeAll()` — `SELECT * FROM txn` без ограничения. На него подписаны одновременно
  `TransactionsViewModel:231`, `ReportViewModel:109`, `AccountBalanceUseCase:49` и —
  постоянно, с момента старта процесса — `WidgetUpdater:39`. Каждое изменение БД перегоняет
  всю таблицу в `List<Txn>` четыре раза.
* `accountBalance(account, transactions)` (`AccountBalanceUseCase.kt:21-35`) для **каждого**
  счёта проходит **все** операции. 20 счетов × 20 000 операций = 400 000 итераций на эмиссию.
  `buildWidgetSnapshot` (`WidgetSnapshot.kt:106-114`) делает то же самое ещё раз.
* Поиск и фильтры (`matchesFilter`, `TransactionsViewModel.kt:116-127`) работают в памяти по
  всему списку на каждое нажатие клавиши.

**Что сделать.** Перенести агрегацию в SQL, оставив чистые функции для того, что действительно
считается в памяти. Новых зависимостей не требуется — Paging не заводить (см. `ROADMAP.md` §10).
1. `TxnDao`: добавить запросы
   `SELECT account_id, currency_code, SUM(...) ... GROUP BY` для балансов (расход/доход/перевод
   учитываются знаком в самом SQL) и `observeRange(from, to)` для отчёта и списка.
   Балансы возвращать как `@Embedded`-проекцию, а не как `TxnEntity`.
2. `AccountBalanceUseCase` строит балансы из проекции: один запрос вместо полного скана.
   Чистая функция `accountBalance(account, transactions)` остаётся — на ней держатся
   существующие тесты и снимок виджета в офлайн-сценариях; но продуктовый путь идёт через SQL.
3. `TransactionsViewModel` подписывается на диапазон дат (по умолчанию — текущий месяц плюс
   загрузка предыдущих по прокрутке), а не на всю таблицу. Фильтр по счёту/категории/валюте
   уходит в `WHERE`.
4. `WidgetUpdater` не должен работать, если виджет не размещён: проверять
   `GlanceAppWidgetManager(context).getGlanceIds(CorrienteWidget::class.java).isNotEmpty()`
   и подписываться только тогда.
5. Замерить до и после на синтетическом наборе: юнит-тест, который генерирует 50 000 операций
   и 20 счетов и проверяет, что расчёт балансов укладывается в разумный бюджет; это не
   микробенчмарк, а защита от возврата O(N·M).

**Критерий приёмки.** На БД из 50 000 операций: открытие списка операций и ввод расхода —
без видимой задержки на эмуляторе; в `logcat` нет `Skipped N frames`.

**Тесты.** `[БД]` тесты новых DAO-запросов на балансы (совпадение с результатом чистой функции
на тех же данных — это и есть контроль корректности SQL). Юнит-тест на объёме из п. 5.

### F2.5 — Мигание «нет счетов» и тупики в пустых состояниях

**Симптом.** При открытии экрана ввода на долю секунды видно «нет счетов», потом появляется
форма. У пользователя без счетов сообщение «нет счетов» — тупик: создать счёт с этого экрана
нельзя, а куда идти, не сказано.

**Причина.** `stateIn(..., TxnEntryUiState(date = form.value.date))` — начальное состояние с
пустым списком счетов (`TxnEntryViewModel.kt:179`), а экран трактует пустой список как
«счетов нет» (`TxnEntryScreen.kt:111`). Различить «ещё не загрузилось» и «действительно пусто»
нечем. Та же болезнь у `TransactionsScreen`, `AccountsScreen`, `ReportScreen`.

**Что сделать.**
1. Ввести в `TxnEntryUiState` (и аналогах) явный признак `loaded: Boolean = false`,
   выставляемый в `combine`-блоке. Пока `!loaded` — не показывать ни форму, ни пустое
   состояние; показывать пустой контейнер или `CircularProgressIndicator`.
2. Пустое состояние сделать действием: «Счетов пока нет» + кнопка «Создать счёт», ведущая на
   экран счетов с открытым редактором. То же для «нет категорий» и «нет операций».

**Критерий приёмки.** Открытие экрана ввода не мигает сообщением; на чистой установке
из пустого состояния можно за два тапа дойти до создания счёта.

**Тесты.** `TxnEntryViewModelTest`: начальное значение `uiState` имеет `loaded = false`,
после первой эмиссии репозиториев — `true`.

### F2.6 — Категории при вводе: горизонтальная лента вместо сетки

**Симптом.** В Monefy категории — сетка иконок, попадание в нужную за один взгляд. Здесь —
горизонтально прокручиваемый ряд чипов (`TxnEntryScreen.kt:131-144`, `ChipRow` на
`horizontalScroll`). При 20+ категориях выбор превращается в прокрутку вслепую; иконки и
цвета категорий, добавленные в T5.5, на этом экране не используются вообще.

**Что сделать.** Заменить `ChipRow` для категорий на `LazyVerticalGrid` (4 колонки) с ячейкой
«иконка + подпись + цвет категории», сохранив выбор «Без категории» первой ячейкой.
Ряд счетов оставить лентой — счетов единицы. Ограничить высоту сетки, чтобы клавиатура и
кнопка сохранения оставались на экране.

**Критерий приёмки.** При 24 категориях все видны без горизонтальной прокрутки; выбор
категории — один тап; иконка и цвет из настроек категории видны на ячейке.

**Тесты.** Логика отбора и сортировки категорий уже во ViewModel и покрыта; визуальная
часть — сценарий 7 §7.

### F2.7 — Экспорт и восстановление без индикатора занятости

**Симптом.** На большой БД экспорт занимает секунды, а экран никак не реагирует: можно нажать
ещё раз и запустить второй экспорт.

**Причина.** `BackupViewModel.kt:33-34` — `busy: StateFlow<Boolean>` заведён и обновляется,
но `SettingsScreen` его не читает (проверено: единственные упоминания `busy` — сам
`BackupViewModel`).

**Что сделать.** Подписать `SettingsScreen` на `busy`: блокировать пункты «Экспорт» и
«Восстановить» и показывать `LinearProgressIndicator` под списком, пока идёт операция.

**Критерий приёмки.** Во время экспорта пункты недоступны, виден индикатор; после завершения
всё возвращается и появляется диалог результата.

**Тесты.** `BackupViewModel` — юнит-тест на переход `busy` false → true → false.

### F2.8 — Калькулятор молча обнуляет отрицательный результат

**Симптом.** Ввод «5 − 10 =» очищает поле, не объясняя почему. Пользователь думает, что
промахнулся по кнопке.

**Причина.** `TxnEntryViewModel.kt:215` — при `result.raw <= 0` подставляется
`AmountInput.empty()`. Это заплатка от прошлого креша (`AmountInput.fromMinor` не принимает
отрицательное, что верно по I-1), но пользователю она выглядит как сбой.

**Что сделать.** Оставить результат отрицательным во внутреннем состоянии (поле `calcAcc`
это уже умеет — `majorText` на строках 64-67 рисует минус) и показать его в поле суммы,
заблокировав «Сохранить» с подсказкой «сумма должна быть больше нуля». Знак операции
по-прежнему определяется её видом (I-1) — отрицательное значение живёт только в
промежуточном состоянии калькулятора и никогда не доходит до `Money`.

**Критерий приёмки.** «5 − 10 =» показывает «−5», сохранение недоступно, подсказка видна;
последующее «+ 20 =» даёт «15» и разблокирует сохранение.

**Тесты.** `TxnEntryViewModelTest`: последовательность нажатий → `amountText` == "−5",
`canSave` == false; продолжение → `canSave` == true.

## 5. Приоритет P3 — полировка и мёртвый код

### F3.1 — Нет иконки приложения

Lint: `MissingApplicationIcon` (`AndroidManifest.xml:5`). В `app/src/main/res` нет ни одной
`mipmap`-папки — Android подставляет системную заглушку. Нарисовать адаптивную иконку
(`ic_launcher` foreground + background + monochrome для тем Android 13+), положить в
`mipmap-anydpi-v26` и растровые фолбэки, прописать `android:icon` и `android:roundIcon`.
Критерий: иконка видна в лаунчере, в списке «Приложения» и в теме иконок.

### F3.2 — `allowBackup` без `dataExtractionRules`

Lint: `DataExtractionRules` (`AndroidManifest.xml:7`). Сейчас `android:allowBackup="false"` —
решение осознанное (данные вывозятся своим бэкапом, ADR-013). Сделать его явным: добавить
`res/xml/data_extraction_rules.xml` и `res/xml/backup_rules.xml`, в которых **всё**
исключено из облачного и device-to-device переноса, и сослаться на них из манифеста.
Это не меняет поведения, но фиксирует намерение и снимает предупреждение.

### F3.3 — Цвет и иконка счёта: поля есть, UI нет, правка их затирает

`AccountEntity` имеет `color` и `icon`. `AccountsViewModel.save` при создании передаёт
`color = 0`, а при редактировании зовёт `accounts.rename(id, name, color = 0, icon = null, ...)`
(`AccountsViewModel.kt:185`) — то есть любая правка счёта безусловно сбрасывает цвет и иконку.
Сегодня незаметно, потому что задать их всё равно негде. Сделать: выбор цвета из
`CategoryPalette` и эмодзи-иконки в редакторе счёта, как это уже сделано для категорий;
`rename` перестаёт принимать `color`/`icon` вслепую. Критерий: цвет счёта виден на экране
счетов и в строках операций, правка имени его не сбрасывает.

### F3.4 — Мёртвый код и предупреждения lint

* `R.string.widget_reset_defaults` не используется — кнопка «Сбросить к значениям по умолчанию»
  на экране настроек виджета не реализована. Либо реализовать (сброс закреплённых валют и
  активного счёта в `WidgetConfigStore`), либо удалить строку. Предпочтительно реализовать:
  без неё из состояния «закрепил не те валюты» выхода нет.
* `ReportViewModel.dominantCurrency` (строка 58) не вызывается из продуктового кода — валюта
  отчёта считается инлайн на строках 118-127. Удалить функцию или использовать её вместо
  дублирующего кода.
* `AutoboxingStateCreation` в `CategoriesScreen.kt:188` и `CurrenciesScreen.kt:132` —
  `mutableIntStateOf`.
* `UseKtx` в `AutoBackupViewModel.kt:55` — `String.toUri()`.
* `UseTomlInstead` в `app/build.gradle.kts:49-55` — пять зависимостей Compose объявлены
  строками мимо version catalog. Перенести в `libs.versions.toml`.
* `UnusedAttribute` в `widget/res/xml/corriente_widget_info.xml:7-8` — `targetCellWidth`/
  `targetCellHeight` только с API 31: вынести в `res/xml-v31`, оставив `minWidth`/`minHeight`
  в базовом файле.

### F3.5 — Activity быстрого ввода экспортированы без нужды

`QuickExpenseActivity` и `ChangeActiveAccountActivity` объявлены `android:exported="true"`
(`AndroidManifest.xml:24-32`). Первая записывает расход, вторая меняет активный счёт — обе
доступны любому приложению на устройстве. `actionStartActivity` в Glance строит `PendingIntent`
от имени самого приложения, экспорт для этого не нужен. Поставить `exported="false"`,
проверить, что тапы в виджете продолжают работать (сценарий 4 §7). Заодно убрать из
`:widget/CorrienteWidget.kt:61` захардкоженный `APP_PACKAGE = "com.corriente.app"` — брать
`context.packageName`, иначе любой `applicationIdSuffix` в будущих типах сборки сломает виджет
молча.

### F3.6 — Доли категорий в отчёте не дают 100 %

`ReportViewModel.withShares:81` — `(total * 100) / grand` целочисленным делением, доли
округляются вниз и в сумме дают 97–99 %. Раздать остаток по методу наибольших остатков
(largest remainder), проверив тестом, что сумма долей ровно 100 при непустом отчёте.

## 6. Порядок исполнения

Строго сверху вниз по приоритетам. Внутри P0 — в номерном порядке: **F0.2 обязана идти
второй**, потому что F0.3–F0.6 и большая часть P1 показывают ошибки через введённый ею
механизм сообщений.

Зависимости между задачами:

```
F0.1  ─────────────────────────────────────────► (независима)
F0.2  ──┬─► F0.3 ─► F0.4                      (сообщения об ошибках)
        ├─► F0.5 ─► F1.2                      (импорт)
        └─► F0.6
F1.1  ─────────────────────────────────────────► (независима)
F1.3  ──► F1.4                                 (бэкап: сначала расписание, потом целостность)
F1.5  ── требует миграции v1→v2, идёт последней в P1
F2.1  ── крупная, делать отдельным подходом; после неё перепроверить F2.2
```

После каждого приоритета — прогон полного ручного сценария §7, а не только затронутых экранов.

## 7. Ручные сценарии на эмуляторе

Запуск: `emulator -avd corriente -no-window -no-audio -gpu swiftshader_indirect -no-snapshot`.
Кириллицу через `adb shell input text` не вводить.

1. **Ввод суммы (F0.1, F2.8).** Расход → 25 раз «9» → приложение живо, поле не растёт после
   18 знаков. Затем «5 − 10 =» → «−5», «Сохранить» недоступно → «+ 20 =» → «15», доступно.
2. **Архивные сущности (F0.3, F0.4).** Создать счёт и категорию, записать операцию,
   заархивировать оба, открыть операцию из списка, поправить заметку, сохранить → счёт и
   категория те же.
3. **Автобэкап (F1.3).** Выбрать папку, включить, «Сделать бэкап сейчас» → в папке файл,
   на экране обновилась дата последнего бэкапа. Отозвать доступ к папке (удалить её) →
   следующий запуск гасит переключатель и показывает ошибку.
4. **Виджет (F0.6, F3.5).** Разместить виджет, тап по категории → быстрый ввод → повернуть
   экран во время сохранения → операция записана ровно один раз. Тап по названию счёта →
   смена активного счёта работает.
5. **Тёмная тема (F2.3).** Системная тёмная тема → холодный запуск без белого кадра;
   быстрый ввод из виджета тёмный.
6. **Вставки (F2.4).** API 36+, жестовая навигация: пройти все экраны, открыть клавиатуру
   на заметке и на поиске — кнопка «Сохранить» и поле ввода видны.
7. **Ввод и отчёт на объёме (F2.1, F2.6).** Импортировать `testdata/monefy_sample.csv`,
   затем сгенерированный файл на 50 000 строк; открыть список, поиск, отчёт — без
   заметных задержек, в `logcat` нет `Skipped … frames`.
