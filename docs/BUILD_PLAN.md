# План разработки Corriente — к исполнению

Этот документ — рабочее задание для агента-исполнителя. Архитектурные обоснования — в
[`ARCHITECTURE.md`](ARCHITECTURE.md), проверяемые правила — в [`INVARIANTS.md`](INVARIANTS.md),
формат импорта — в [`MONEFY_IMPORT.md`](MONEFY_IMPORT.md).

Все решения приняты, открытых блокирующих вопросов нет (§7).

---

## 0. Правила работы (обязательны для исполнителя)

1. **Перед каждой задачей — прочитать `docs/INVARIANTS.md`.** Это не формальность: половина
   инвариантов существует потому, что нарушение даёт тихую ошибку в деньгах, которую не поймает
   ни компилятор, ни ревью.
2. **Задача не считается сделанной без теста.** Исключение — только чисто визуальные Composable;
   их логика всё равно выносится в ViewModel/чистые функции и тестируется там.
3. **Зависимости — только из §1.3.** Появление любой новой библиотеки требует явного согласования.
   Особенно: **никаких сетевых библиотек** (ADR-013).
4. **Никаких «умных» абстракций.** Без Arrow, без generic-репозиториев «на все случаи»,
   без собственных DSL, без рефлексии, без кодогенерации кроме Room и kotlinx-serialization.
   Прямолинейный код, который целиком читается за один заход, — цель, а не компромисс.
5. **Если инвариант мешает сделать задачу — остановиться и спросить.** Не обходить, не «временно
   нарушить», не оставлять TODO. Инвариант, который мешает, либо неверен (и его надо изменить
   осознанно), либо задача поставлена неправильно.
6. **Один коммит на задачу**, сообщение начинается с ID задачи: `T1.4: категории — CRUD`.
7. **Перед коммитом:** `./gradlew detekt test` зелёный. Красный тест не коммитится никогда,
   даже «чтобы не потерять работу» — для этого есть отдельная ветка.
8. **Не расширять скоуп задачи.** Заметил проблему за пределами задачи — записал в
   `docs/BACKLOG.md`, продолжил.

## 1. Целевая конфигурация

### 1.1 Платформа

| Параметр | Значение | Обоснование |
|---|---|---|
| Язык | Kotlin, JVM target 17 | — |
| `minSdk` | **26** | `java.time` доступна без desugaring; телефон 2018+ года. Изменение — одна строка, если понадобится ниже |
| `targetSdk` / `compileSdk` | последние стабильные на момент старта | — |
| UI | Jetpack Compose, Material 3 | — |
| Архитектура | одна `Activity` + Compose-навигация; MVVM без «чистой архитектуры» с тремя слоями DTO | Объём проекта не оправдывает маппинги между тремя моделями |
| Разрешения | **никаких.** В манифесте не должно быть ни одного `<uses-permission>`, кроме тех, что реально нужны SAF (а ему не нужны) | I-24 |

### 1.2 Версии

Взять **последние стабильные** на момент старта и зафиксировать в `gradle/libs.versions.toml`.
Версии из памяти не использовать — проверить в актуальных релиз-нотах.

Известный якорь на 08.2026: `androidx.glance:glance-appwidget` — стабильная **1.1.1**
(1.2.0 всё ещё в rc, 1.3.0 в alpha). Брать стабильную; если к моменту старта 1.2.0 стала stable — брать её.

### 1.3 Разрешённые зависимости

```
Kotlin stdlib, Coroutines
androidx.compose (BOM), material3, activity-compose, navigation-compose, lifecycle-viewmodel-compose,
material-icons-extended (иконки нижней навигации — в -core их нет)
androidx.room: runtime, ktx, compiler (KSP), testing
androidx.datastore: preferences
androidx.glance: glance-appwidget, glance-material3        (с этапа 4)
androidx.work: work-runtime-ktx                            (с этапа 5, только автобэкап)
org.jetbrains.kotlinx: kotlinx-serialization-json
com.github.doyaaaaaken: kotlin-csv-jvm                     (с этапа 3)
тесты: junit4, kotlinx-coroutines-test, androidx.room:room-testing, robolectric (только если без него никак)
статика: detekt
```

Всё, чего нет в списке, — согласовывать.

### 1.4 Структура

```
:core:money     чистый Kotlin, без Android SDK. Money, Currency, парсинг/форматирование
:core:data      Room, DAO, репозитории, миграции, CSV-импорт, бэкап, DataStore
:app            Compose UI, ViewModel, навигация, DI-контейнер
:widget         Glance-виджет и построитель снимка                (появляется на этапе 4)
```

Зависимости: `:app` → `:core:data` → `:core:money`; `:widget` → `:core:data`.
`:core:money` **не должен** компилироваться с Android SDK — это проверяется тем, что он
объявлен как `kotlin("jvm")`, а не как android-библиотека.

### 1.5 Запрещено (проверяется Detekt и ревью)

* `Double` / `Float` в `:core:money`, `:core:data` и в любых моделях, где есть деньги (I-1).
* `NumberFormat.getInstance()`, `String.toDouble()`, `DecimalFormat` при разборе денежных строк (I-25).
* `fallbackToDestructiveMigration()` в любом виде (I-20).
* `<uses-permission android:name="android.permission.INTERNET" />` (I-24).
* Любые обращения к сети, включая «безобидные» проверки обновлений.
* Хранение агрегатов как источника истины (I-9).

## 2. Этап 0 — фундамент (6–10 ч ревью)

Пользовательской функциональности не появляется. Это единственный этап, который нельзя
делать «побыстрее»: всё остальное строится на нём.

**T0.1 Скелет проекта.** Gradle, version catalog, четыре модуля (`:widget` — пустой заглушкой
или отложить до этапа 4), пустая `MainActivity`, Detekt с правилами из §1.5.
*Готово:* `./gradlew assembleDebug detekt test` зелёный, приложение запускается и показывает пустой экран.

**T0.2 `:core:money`.**
```kotlin
@JvmInline value class CurrencyCode(val code: String)   // ISO-4217, валидация в init
@JvmInline value class Minor(val raw: Long)
data class Currency(val code: CurrencyCode, val minorUnits: Int, val displayScale: Int, val symbol: String)
data class Money(val amount: Minor, val currency: CurrencyCode)
```
Операции: `plus`, `minus`, `unaryMinus`, `times(Int)`, `compareTo` (только при равенстве валют),
`sumOf` для списка одной валюты.
*Готово:* тесты на I-1, I-2, I-3, I-4 — включая падение при сложении разных валют
и падение при переполнении `Long`.

**T0.3 Парсинг и форматирование сумм.** Явный парсер пользовательского ввода
(`"1 234,56"`, `"1234.56"`, `"1,234.56"` → `Minor`) с однозначными правилами и тестами
на все формы; форматирование по `displayScale`.
*Готово:* тест I-25; тест «парсер не зависит от `Locale.setDefault()`» — прогнать те же кейсы
под `Locale.US` и `Locale("ru","RU")`, результат обязан совпасть.

**T0.4 Схема БД v1.** Room-сущности `currency`, `account`, `category`, `txn`, `import_batch`,
`import_alias`, `app_setting` по §3.2 `ARCHITECTURE.md`, все индексы и `CHECK`.
`exportSchema = true`, схема коммитится. Сид справочника валют полным списком ISO-4217
(код, exponent, символ; `is_active = 0` у всех, кроме RUB/USD).
*Готово:* тест открытия БД; тест сида (в таблице >150 валют, у CLP `minor_units = 0`);
каркас `MigrationTestHelper` с тестом-заглушкой v1→v1, чтобы механизм был готов заранее.

**T0.5 Защитные тесты.** Тест, читающий `AndroidManifest.xml` и падающий при появлении
любого `uses-permission`; Detekt-правило на запрещённые импорты и вызовы из §1.5.
*Готово:* оба теста падают, если правило нарушить (проверить намеренным нарушением, потом откатить).

**Приёмка этапа 0:** `:core:money` не зависит от Android; все тесты зелёные; схема
закоммичена; попытка написать `Double` в денежном коде роняет сборку.

## 3. Этап 1 — учёт (14–20 ч)

После этого этапа приложением уже можно пользоваться.

**T1.1 Каркас приложения.** DI-контейнер вручную (`AppContainer` в `Application`), навигация,
нижняя навигация: «Операции», «Счета», «Отчёт», «Настройки».

**T1.2 Валюты.** Экран выбора активных валют из ISO-справочника: поиск по коду/названию,
переключатель `is_active`, редактирование `display_scale` и символа.
*Готово:* тест ViewModel; вручную — включить KZT и CLP, убедиться, что CLP показывается без копеек.

**T1.3 Счета.** CRUD, валюта выбирается только из активных, **после первой операции поле валюты
недоступно** (I-23), архивирование вместо удаления при наличии операций, начальный остаток,
`include_in_total`.
*Готово:* тест «попытка сменить валюту счёта с операциями — отказ».

**T1.4 Категории.** CRUD, тип EXPENSE/INCOME, одна степень вложенности, цвет/иконка,
архивирование, слияние двух категорий (понадобится после импорта).
*Готово:* тест слияния (операции переезжают, исходная категория исчезает).

**T1.5 Ввод операции.** Крупная цифровая клавиатура, выбор счёта, категории, даты, заметка.
Знак определяется типом, не вводится (I-1, `CHECK amount_minor > 0`).
Валюта операции берётся из счёта и не выбирается (I-15).
*Готово:* тест ViewModel на все ветки валидации; вручную — добавить расход в RUB и в USD.

**T1.6 Список операций.** Группировка по дням, заголовок дня с итогом **по каждой валюте отдельно**,
редактирование, удаление, фильтр по счёту и по валюте, бесконечная прокрутка без Paging
(6 943 строки грузятся целиком — проверить, что не тормозит).
*Готово:* тест запроса; вручную — прокрутка на 7 000 записях плавная.

**T1.7 Балансы.** Главный экран: счета, сгруппированные по валютам, с итогом по каждой валюте.
**Ни одного числа, суммирующего разные валюты** (I-8).
*Готово:* тест расчёта баланса (начальный остаток + доходы − расходы ± переводы).

**T1.8 Отчёт по категориям.** Период (месяц/квартал/год/произвольный) + селектор валюты,
список категорий с суммами и долями, тап по категории → операции.
*Готово:* тест агрегации на фиксированном наборе.

**T1.9 Бэкап.** Экспорт всей БД в JSON через SAF (`ACTION_CREATE_DOCUMENT`), импорт с проверкой
версии схемы и полным замещением данных, подтверждение перед замещением.
*Готово:* round-trip тест (экспорт → очистка → импорт → данные идентичны, включая UUID);
вручную — файл открывается в текстовом редакторе и читается.

**Приёмка этапа 1:** можно за вечер завести счета в трёх валютах, внести операции,
увидеть балансы по валютам, выгрузить и восстановить бэкап.

## 4. Этап 2 — переводы (5–8 ч)

**T2.1 Модель.** Use-case создания/редактирования перевода: одна строка `txn` с `kind=TRANSFER`,
двумя счетами и двумя суммами. Валидация: счета разные, суммы > 0, валюты равны валютам счетов.
*Готово:* тесты I-7а, I-11, I-12; тест «перевод не может существовать половинкой».

**T2.2 UI.** Экран перевода: откуда/куда, две суммы (вторая появляется только если валюты разные),
под полями — выведенный курс сделки («1 USD = 86.95 RUB»), пересчёт второго поля при вводе курса
вручную (курс — вспомогательный ввод, хранятся всегда суммы).
*Готово:* тест ViewModel на пересчёт в обе стороны.

**T2.3 Исключение из отчётов.** Переводы не попадают в доходы/расходы и в отчёт по категориям.
*Готово:* тест на наборе, где перевод сделан внутри отчётного периода.

**Приёмка этапа 2:** перевод 8 695 ₽ → 100 $ меняет оба баланса, не появляется ни в доходах,
ни в расходах, и показывает курс 86.95.

## 5. Этап 3 — импорт из Monefy (8–14 ч)

Спецификация формата — `docs/MONEFY_IMPORT.md`, читать целиком перед началом.

**T3.1 Парсер.** Чтение файла, разбор по правилам §1–2 спецификации.
*Готово:* тесты на `testdata/monefy_sample.csv` строго по `testdata/monefy_sample.expected.md` —
включая `"49,120"` → 4 912 000 минорных единиц, `-1,250.75` → −125 075, категорию с запятой,
две колонки `currency`.

**T3.2 Классификация и склейка.** Псевдокатегории (`Initial balance`, `To '…'`, `From '…'`),
парность переводов по дате и модулю `converted amount`, `NEEDS_REVIEW` для неоднозначных пар,
непарных половинок и аномальной валюты.
*Готово:* тесты на все три случая `NEEDS_REVIEW` из `expected.md`.

**T3.3 Dry-run.** Экран предпросмотра: что будет создано (счета, категории, операции, переводы,
остатки), что помечено `NEEDS_REVIEW` с возможностью решить прямо здесь, что не распарсилось.
Запись — только после явного подтверждения.
*Готово:* вручную на реальном файле — отчёт показывает 6 932 операции, 4 перевода, 3 остатка,
5 счетов, 64 категории, 2 аномалии.

**T3.4 Запись и откат.** Батч в одной транзакции БД, `import_hash` с индексом повторения внутри дня,
повторный импорт того же файла даёт 0 новых строк, откат батча одной кнопкой.
*Готово:* тест идемпотентности (импорт дважды → количество строк не изменилось);
тест отката (после отката БД в исходном состоянии, осиротевшие категории удалены).

**T3.5 Приёмка на реальных данных.** Сверка годовых контрольных сумм из §6 спецификации.
*Готово:* все семь лет сходятся до копейки; расхождения не «объясняются», а отсутствуют.

**Приёмка этапа 3:** история за 2020–2026 в приложении, цифры совпадают с Monefy.
**Здесь Monefy можно удалять.**

## 6. Этап 4 — виджет (8–15 ч)

**T4.1 Снимок.** `WidgetSnapshot` (§4.2 `ARCHITECTURE.md`) — чистая функция от данных,
результат в DataStore. Обновление после каждой записи в БД и раз в сутки.
*Готово:* юнит-тест построителя снимка; форматирование сумм — строками (I-1).

**T4.2 Виджет.** Glance, два размера: компактный (балансы закреплённых валют) и расширенный
(+ быстрые категории). `GlanceTheme.colors`, поддержка тёмной темы.
*Готово:* вручную на устройстве, включая перезагрузку телефона и убийство процесса приложения.

**T4.3 Быстрый ввод.** Тап по категории → полупрозрачная `Activity` с клавиатурой → сохранение
→ немедленное обновление виджета.
*Готово:* вручную; проверить сценарий «приложение выгружено из памяти».

**T4.4 Настройки виджета.** Закрепление 1–3 валют, выбор активного счёта, смена активного счёта
тапом по его названию в виджете.
*Готово:* вручную.

**Приёмка этапа 4:** трата добавляется с домашнего экрана, баланс обновляется сразу,
после переезда в другую страну активный счёт меняется одним тапом.

## 7. Этап 5 — полировка (10–20 ч, ограничить по времени)

**T5.1** Автобэкап по расписанию (WorkManager) в выбранную папку, ротация последних N файлов,

**T5.5** Иконки и цвета категорий, Material You, тёмная тема, калькулятор в поле суммы.

## 8. Готовность к пуску

**Решено и зафиксировано:** модель денег, схема БД, отсутствие конвертации и сети,
структура модулей, набор библиотек, формат импорта, порядок этапов, критерии приёмки.

**Сознательно оставлено на усмотрение исполнителя:** внешний вид экранов (кроме требования
«ни одного числа, суммирующего разные валюты»), названия пакетов и классов, детали навигации,
формат JSON-бэкапа (при условии: версия схемы внутри, человекочитаемость, round-trip).

**Что исполнитель обязан спросить, а не решить сам:**
1. Изменение любого инварианта.
2. Добавление зависимости вне §1.3.
3. Любая необходимость сети.
4. Изменение схемы БД после этапа 3 (там уже живые данные — нужна миграция и бэкап).
5. Всё, что делает какой-либо экран обязательным потребителем курсов валют.

**Первая задача исполнителя:** T0.1. Ветка — `claude/android-finance-tracker-arch-1akrwb`
или новая от неё; план и инварианты уже в репозитории.
